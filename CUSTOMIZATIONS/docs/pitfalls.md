# 历史坑点 / Pitfalls

> **这是什么**：本仓库（acp-client-custom）开发与排查中**踩过的坑**的沉淀。新会话动手前先扫一眼标题，
> 避免重复踩坑。每条写清：现象 → 根因 → 解法 → 验证方式。
>
> **维护铁律**：每解决一个"反复折腾才定位到"的问题，就来这里加一条（一次没定位到就解决的不算坑）。
> 配套：代码位置反查见 [`../architecture.md`](../architecture.md)。

---

## 1. 上游没有任何版本 tag → "按 tag 定基线"的机制直接失效

- **日期**：2026-09-23（初始配置）
- **现象**：照搬 chatbox 的初始化脚本（`git tag -l "v*" --sort=-v:refname | head -1` 取最新 tag 作为
  vendor 基线）会拿到**空字符串**；`registry.md` 的 `current_upstream_version` 无值可填，
  `vendor/vX.Y.x` 分支名 fallback 逻辑也失去意义。
- **根因**：`formulahendry/vscode-acp` 从建仓至今**从未打过 tag**，只有 `main` 分支。
  chatbox 的整套机制建立在上游有稳定 tag 的假设上。
- **解法**：
  1. vendor 基线分支固定为 **`vendor/main`**（不再按 `vX.Y.x` 建线）；
  2. `current_upstream_version` 取**上游 `package.json` 的 `version` 字段**（如 `0.2.0`）——
     它只表达语义版本，**不足以定位代码**；
  3. 唯一定位靠 `current_upstream_commit`（上游 `main` 的 commit hash），两者必须同时准确。
- **教训**：跨仓库移植一套机制前，**先用 `git ls-remote --tags <upstream>` 验证机制依赖的前提**
  （有没有 tag、有没有 release、默认分支叫什么），别假设另一个仓库的约定成立。
- **验证**：`git rev-parse upstream/main` 与 registry frontmatter 一致；
  `pwsh CUSTOMIZATIONS/scripts/init-repo.ps1` 可重复执行不报错。

## 2. 命令 id / 视图 id / 配置键是**全局命名空间** → 改 publisher 不足以让 fork 与上游并存

- **日期**：2026-09-23（初始配置，CUSTOM-20260923-001）
- **现象**：改掉 `package.json` 的 `publisher`/`name`（扩展 id 变成 `zouv.acp-client-custom`）后，
  与上游 `formulahendry.acp-client` 同时安装仍然冲突：命令面板出现重复命令、
  开发者工具报 command already exists、配置项互相覆盖。
- **根因**：VS Code 的 **command id、view id、viewContainer id、configuration section key**
  都在**整个 IDE 实例内全局唯一**，与"哪个扩展贡献的"无关。扩展 id 只决定扩展身份，不决定这些命名空间。
  上游用了 `acp.*` 前缀，fork 原样沿用就必然撞车。
- **解法**：全量重命名 `acp.*` → `acpc.*`，覆盖：
  - `package.json`：21 个命令 id、视图容器 id（`acp-client`→`acp-client-custom`）、
    视图 id（`acpc-sessions`/`acpc-chat`）、配置段（`acpc.agents` 等 4 项）、上下文键（`acpc.turnInProgress`）
  - `src/`：`registerCommand` / `executeCommand` 的字符串字面量、`getConfiguration('acp')`、
    `createTreeView` / `viewType`、`createOutputChannel` 的名称
  - `package.json` 的 `contributes.menus.*.when` 里 `view == acp-sessions` 这类**长字符串内的片段**
- **教训**：
  1. **TypeScript 编译器不检查字符串字面量**——`npm run compile` 全绿**不代表改干净了**，
     必须 `grep -rn` 反向复核残留；
  2. fork 一个 VS Code 扩展前，第一件事是列出它占用的**全局命名空间清单**，而不是先改 publisher。
- **验证**：`grep -rn "acp\.\|acp-sessions\|acp-chat" src/ package.json` 无（非故意保留的）残留；
  两个扩展同时安装后控制台无冲突告警。详见 `registry.md` 的 CUSTOM-20260923-001。

## 3. 批量替换的模式边界：太紧会漏、太松会误伤（同一类错误，两个方向都踩过）

- **日期**：2026-09-23（做坑点 2 的重命名时踩到"太紧"；做 007 的 `sh`→`bash` 时踩到"太松"）
- **现象（太紧→漏）**：用 `s/"acp-sessions"/"acpc-sessions"/g` 批量替换，`package.json` 里
  `"id": "acp-sessions"` 改成功了，但 `"when": "view == acp-sessions"` 里的 `acp-sessions`
  **原封不动**——渲染出的菜单条件全部失效。
- **现象（太松→误伤）**：用 `s|sh CUSTOMIZATIONS/scripts/|bash CUSTOMIZATIONS/scripts/|g` 批量替换，
  模式的 `sh` 子串匹配到了 `pw**sh** CUSTOMIZATIONS/scripts/`，把 4 处 `pwsh` 改成了 **`pwbash`**。
- **根因**：两者是同一个问题的两面——**模式没锚定到词/引号的边界**。
  太紧时（带引号）匹配不到长字符串内的片段；太松时（裸 `sh`）会咬进别的单词里。
- **解法**：
  - 太紧 → 对长字符串内的片段补独立模式（`s/== acp-sessions/== acpc-sessions/g`），
    或一开始就用**不带引号边界的词形模式**；
  - 太松 → 加左边界，例如 `s|\bsh CUSTOMIZATIONS/scripts/|bash ...|g`，
    或用 `([^a-z]|^)sh ` 之类避免咬进 `pwsh`。
- **教训**：
  1. 批量重命名/替换必须**双向验证**——正向确认替换发生，**反向 grep 确认没有残留**；
  2. 还要**同时 grep 被误伤的目标**（本次若没顺手查 `pwbash`，`pwsh` 调用说明就被悄悄改坏了）；
  3. 写完 sed 别只看"改了多少处"，要 `git diff` 扫一眼**改动内容**是否符合预期。
- **验证**：`grep -rn "== acp-" src/ package.json` 为空；`grep -rn "pwbash"` 为空。

## 4. 两处 `acp.` 是**扩展内作用域**，不该跟着重命名

- **日期**：2026-09-23（做坑点 2 的重命名时识别出）
- **现象**：无脑全量替换 `acp.` → `acpc.` 会把两处**不该改**的地方一起改掉：
  1. `src/core/SessionHistoryStore.ts` 的 `const STATE_KEY = 'acp.sessionHistory.v1'`
  2. `src/core/ConnectionManager.ts` 的 `clientInfo.name = 'vscode-acp-client'`
- **根因**：
  1. `STATE_KEY` 是 `workspaceState` 的 **Memento key**，作用域是**当前扩展自己**，
     不与上游冲突；**改了它 = 既有用户的会话历史全部读不出来（等于丢失）**。
  2. `clientInfo.name` 是 ACP `initialize` 握手时**上报给 agent 的客户端标识**，属协议元数据，
     不参与 VS Code 命名空间，改不改都不冲突。
- **解法**：两者**保持原值**，并在 `architecture.md §4` 明确写"故意保留，勿顺手修"。
- **教训**：重命名前先分清两类字符串——
  **全局可冲突标识符**（必须改）vs **扩展内作用域 / 协议元数据**（不该改）。
  判断标准：这个字符串会不会被**别的扩展**在同一命名空间里也用？会 → 改；不会 → 别动。
- **验证**：改完后 `grep -n "STATE_KEY" src/core/SessionHistoryStore.ts` 仍为 `'acp.sessionHistory.v1'`。

## 5. 上游 `acpc.turnInProgress` 上下文键从未 `setContext` → Escape 取消是死绑定

- **日期**：2026-09-23（初始配置扫描时发现，**尚未修复**）
- **现象**：`package.json` 里两处依赖 `acpc.turnInProgress`（改名前的 `acp.turnInProgress`）：
  - `keybindings`：`escape` → `acpc.cancelTurn`，条件是 `when: acpc.turnInProgress`
  - `menus.view/title`：取消按钮的可见性条件 `view == acpc-chat && acpc.turnInProgress`

  但 `grep -rn "setContext" src/` **没有任何结果**——这个上下文键从来没有人设置过，
  因此上述两条的 `when` 恒为 false：**Escape 键取消不了当前轮次，取消按钮也不显示**。
- **根因**：上游遗留——贡献点声明了上下文键，但实现里漏了
  `vscode.commands.executeCommand('setContext', 'acpc.turnInProgress', <bool>)`。
- **解法**：**本次未修**（超出"初始配置"范围）。修复方向：在 `SessionManager` 的
  `promptStart`/`promptEnd`（或对应事件）回调里设置该上下文键，与
  `ChatWebviewProvider` 的 `promptStart`/`promptEnd` 消息同源。
- **教训**：`when` 子句里引用的每个上下文键，都要 `grep setContext` 确认有 setter；
  贡献点的"声明"和"实现"分处两个文件，很容易只有一半。
- **验证**（修复后）：发一条消息，确认取消按钮出现且 Escape 能中断当前轮次。
- **复发记录（2026-09-25，CUSTOM-20260925-057）——换了张皮：`acpc.defaultWorkingDirectory`**。
  这个设置在 `package.json` 里声明得好好的（type/默认值/description 齐全），
  **而 `grep defaultWorkingDirectory src/` 零命中**——从来没有一行代码读过它。
  形态与 #5 完全同源：**声明在一个文件、实现在另一个文件，而只有一半**。
  区别是它不报错、不失效得很明显：它静默地什么都不做，用户设了也没反应，
  于是很容易被当成"哦这个设置没用"而不是"这是个缺陷"。用户正是在要"每会话切换工作目录"时才撞上它。
  **教训升级**：`package.json` 的 `contributes.configuration` 也是一种"声明"，
  它与 `when` 子句、与 `contributes.commands` 一样，都需要一条"有没有实现"的反向核对。
  可操作的判据：**给每个 `acpc.*` 设置项 grep 一次读取点**；没有读取点的，
  要么接上（本次）、要么删掉（不留死声明）。
  （同类清单：`contributes.commands` 的 22 个命令、`viewsContainers` 的视图 id，
  也适用"声明↔实现双向核对"这条纪律。）

## 6. `.vscodeignore` 不与顶层目录联动 → 自定义内容被打进 `.vsix` 发给用户

- **日期**：2026-09-23（初始配置，CUSTOM-20260923-003）
- **现象**：新建 `CUSTOMIZATIONS/`、`.agents/`、`AGENTS.md` 后直接 `vsce package`，
  这些**开发机制文件会全部进入 `.vsix`**（vsce 默认打包仓库里除忽略项外的一切），
  安装包体积变大，且把内部开发文档、改动账本、坑点库发给终端用户。
- **根因**：`.vscodeignore` 是**白名单式的反向排除**（列出"不打包什么"），
  上游只排除了它自己知道的路径；新增顶层目录不会自动被排除。
- **解法**：每新增一个顶层目录/文件，同步往 `.vscodeignore` 加一条；本次加了
  `CUSTOMIZATIONS/**`、`.agents/**`、`.claude/**`、`AGENTS.md`、`release/**`、`.github/**`。
- **教训**：`.vscodeignore` 和顶层目录是**联动契约**——架构变更（加目录）时容易忘。
  打包后用 `npx @vscode/vsce ls --tree` 验证产物清单。
- **验证**：`npx @vscode/vsce ls --tree | grep -i "customiz\|agents\|AGENTS"` 无输出。

## 7. 上游以 CRLF 入库 + 本机 `core.autocrlf=true` → 编辑一次就整文件伪差异

- **日期**：2026-09-23（首次提交前发现，差点带着 14000 行伪差异提交）
- **现象**：准备提交时 `git diff --stat` 显示 `src/ui/ChatWebviewProvider.ts | 5121 +-`、
  `package.json | 852 +-`——但实际只改了几行；整仓统计 14339 插入 / 12788 删除。
- **根因**：
  1. 上游 `formulahendry/vscode-acp` 的 blob **以 CRLF 入库**（仓库里**没有 `.gitattributes`**，
     推测作者在 Windows 上未开 autocrlf 直接提交）；
  2. 本机 `core.autocrlf=true`（`C:/Program Files/Git/etc/gitconfig` 与 `~/.gitconfig` 都设了），
     但 autocrlf 对**已是 CRLF 的 blob** 不做归一化，两边就这么"相安无事"地一致着；
  3. 编辑工具一介入就打破平衡：**`sed -i`、`Write` 工具、`npm install` 都产出 LF**，
     而 `Edit` 工具会保留文件原有换行。于是一部分文件被转成 LF，与 CRLF blob 逐行不等 → 整文件 diff。
- **危害**：不只是 diff 难看——**后续每次合并上游都会变成全文件冲突**，三方合并能力彻底丧失。
- **解法**（三层）：
  1. 加 `.gitattributes` 写 `* -text`：关闭 git 的换行转换，按字节原样存取，
     保证本地 blob 与上游 blob 逐字节可比对（`-text` 只关 EOL 转换，不影响 diff/merge）；
  2. `CUSTOMIZATIONS/scripts/normalize-eol.mjs` 做批量归一化 + `--check` 只读自检；
  3. 自检接入 `check-registry.mjs` §4；`release-vsix.sh` 在 `npm install` 之后自动把 `package-lock.json` 转回 CRLF。
- **判据（两类文件，别一刀切）**——修的过程中踩到的第二个坑：

  | 类别 | 路径 | 换行 | 理由 |
  |---|---|---|---|
  | **上游共有** | `src/`、`package*.json`、`.github/`、`.gitignore`、`.vscodeignore`、`tsconfig.json` … | **CRLF** | 与上游 blob 逐行可比，否则合并全冲突 |
  | **纯自定义** | `CUSTOMIZATIONS/`、`.agents/`、`AGENTS.md`、`.gitattributes` | **LF** | 不与上游同名，无冲突风险 |

  **纯自定义文件必须保持 LF——尤其是 `.sh`**：带 CRLF 的 shell 脚本在 Linux/macOS 上会因
  shebang / 命令解析带上 `\r` 而直接执行失败。第一版 `normalize-eol.mjs` 把"所有已跟踪文件"
  一刀切成 CRLF，提交后自检立刻抓到 `sync-vendor.ps1` 被误判——**同一份规则里，两个方向都错得起来**。
- **教训**：
  1. **fork 一个仓库、动手改之前，先确认它的换行符约定**——`git ls-files --eol` 或
     `git cat-file blob HEAD:<file> | xxd | head` 看一眼真实字节，别等提交时才发现；
  2. **测量换行符不要用 Git Bash 的 `grep -U`**——它可能仍走文本模式，读数会骗人；
     用 node/python 直接读字节才准（本次就被误导过一次）；
  3. 判断"有没有真改动"看 `git diff --numstat` 的数字，数值离谱基本就是换行符问题；
  4. **写"归一化"类工具时先想清楚分类**，别默认全局一个规则——本次先过度归一（把 .sh 转 CRLF），
     才补上 CUSTOM_ONLY 判据。好在自检脚本在提交后立刻暴露了它。
- **验证**：`node CUSTOMIZATIONS/scripts/normalize-eol.mjs --check` 报"全部 36 个上游共有文件一致（CRLF）"；
  `git diff --numstat src/extension.ts` 从 `544/544` 降到真实改动量。

## 8. macOS 自带 bash 3.2 → `declare -A` 报 "invalid option"（本地永远复现不了）

- **日期**：2026-09-23（把自检接进 CI 三平台矩阵后立刻被 macos-latest 抓出，CUSTOM-20260923-008）
- **现象**：CI 里 ubuntu 与 windows 都过，**macos-latest 挂在自检步骤**：
  ```
  check-registry.sh: line 17: declare: -A: invalid option
  declare: usage: declare [-afFirtx] [-p] [name[=value] ...]
  ##[error]Process completed with exit code 2.
  ```
- **根因**：**macOS 自带的 `/bin/bash` 是 3.2 版（2007 年）**——苹果因 GPLv3 授权问题一直没升级它。
  关联数组 `declare -A` 需要 bash 4.0+，所以直接不可用。
  而开发机上的 Git Bash 是 bash 5.x，**本地怎么跑都是绿的**，问题只会在 CI（或别人的 Mac）上出现。
- **解法**：把自检脚本整体**移植到 Node**（`check-registry.mjs`），删掉 bash 版。
  选 Node 而不是"绕开关联数组改写 bash"的理由：
  1. Node 在本项目是**硬依赖**（`npm install` 是前置步骤，不可能没有）；
  2. 项目里 `normalize-eol.mjs` 已有先例，语言统一；
  3. 一次性消除 Windows / Linux / macOS 的 **shell 方言**差异——而 CI 恰恰是三平台跑的。
- **教训**：
  1. **shell 脚本的可移植性比想象中差得多**：关联数组、`mapfile`、`sed -i` 语义、`grep -P`……
     在 macOS(BSD) 与 Linux(GNU) 上差异一堆，而 macOS 还锁在 bash 3.2。
     **凡是 CI 要在多平台跑的脚本，优先用 Node/Python，别用 bash**；
  2. **"本地能跑"不等于"能跑"**——本地 Git Bash 是 bash 5，掩盖了 macOS 的问题。
     把检查放进多平台 CI 的价值就在这里：**这次是 CI 替我们发现的，不是用户**；
  3. 移植脚本时要**对照原实现验证等价性**（本次移植初版有 bug，含标记文件数从 12 误报成 2，
     靠与 bash 版对照计数才发现），并用**反向测试**（故意破坏 → 确认能报错 → 还原）证明检测真的有效。
- **验证**：`node CUSTOMIZATIONS/scripts/check-registry.mjs` 输出与 bash 版一致（12 个含标记文件）；
  CI 三平台的 job 全部通过（macOS 的测试步骤另见 #9）。

## 9. macOS runner 上 `npm test` 必失败 → 上游既有问题，别去修

- **日期**：2026-09-23（修完 #8 后 CI 仍红，追查到是另一回事，CUSTOM-20260923-009）
- **现象**：macos-latest 的 `npm test` 报
  ```
  - Downloading (299.02 MB)
  ✔ Downloaded VS Code into .../.vscode-test/vscode-darwin-arm64-1.139.0
  Test error: Error: spawn .../Visual Studio Code.app/Contents/MacOS/Electron ENOENT
  ```
- **根因**：**299 MB 不可能 12 秒下完**——"Downloaded" 是假的，**解压静默失败**，
  所以 Electron 二进制根本不存在。属 `@vscode/test-electron` 在 macOS arm64 runner 上的工具链问题。
- **关键证据（决定了"不该自己修"）**：查上游仓库的 CI 历史——
  `gh run list -R formulahendry/vscode-acp` 里**没有一次成功**，全是 `failure` / `action_required`。
  说明这是上游既有的问题，不是本仓库引入的，也不该由本仓库去修。
- **解法**：**不修**。macOS 上仍然跑机制自检与打包（跨平台自检覆盖必须保留——
  正是它在 macOS 上抓出了 #8 的 bash 3.2 问题），只跳过启动 VS Code 的测试步骤：
  ```yaml
  - run: npm test
    if: runner.os == 'Windows'     # Linux 走 xvfb-run，macOS 跳过
  ```
  等上游/工具链修好后再放开。
- **教训**：
  1. **CI 红了先分清"谁的问题"**——查上游仓库的 CI 历史（`gh run list -R <upstream>`）是一分钟的事，
     能立刻区分"我引入的"与"上游既有的"，避免一头扎进去修不属于自己的坑；
  2. **不要用 `continue-on-error` 掩盖**——那会让 build 显示绿、实际有失败，掩盖真问题。
     要用显式的 `if` 跳过 + 注释写清楚原因与证据；
  3. 判断"跨平台检查要不要保留"时看**它有没有真的抓到过东西**：

## 10. `git ls-files` 只列**已跟踪**文件 → 新建未提交的文件静默绕过所有文件级检查

- **日期**：2026-09-23（Chat 面板重写 Phase 2 新增 `src/ui/chat/` 25 个文件时发现，CUSTOM-20260923-011）
- **现象**：25 个新建的 `.ts` 文件实际是 **LF**（Write 工具产出），但
  `node CUSTOMIZATIONS/scripts/normalize-eol.mjs` 报
  `所有文件已是 CRLF，无需修正`，`--check` 也报 `[OK] 全部 36 个上游共有文件换行符一致`。
  **检查通过了，但事实是错的。**
- **根因**：`normalize-eol.mjs` 用
  ```js
  execFileSync('git', ['ls-files'], ...)   // ← 默认只列 index 里的文件
  ```
  新建文件在 `git add` 之前不在 index 里，于是**根本不在被检查的名单上**。
  修复后同一命令立刻报出 25 个文件需要转换——**修复前后差 25 个文件**。
- **危害范围比 EOL 更大**：这是**「用 `git ls-files` 当文件清单」这一类做法**的通病。
  仓库里任何"遍历文件做检查"的脚本（含未来的 lint/扫描类脚本）只要用默认参数，
  都会对未提交的新文件视而不见——而新文件恰恰是最需要检查的对象。
- **解法**：
  ```js
  execFileSync('git', ['ls-files', '--cached', '--others', '--exclude-standard'], ...)
  //                                              ^^^^^^^^^^^^^^^^^^^^^^^^^^^^
  //                              同时列出未跟踪文件；--exclude-standard 仍遵守 .gitignore
  ```
  与 `acp-record-change` skill 里枚举改动文件用的正是同一组参数。
- **教训**：
  1. **检查器"通过"不等于"检查过了"**——要问一句「它到底扫了哪些文件？数量对不对？」。
     本次是靠**直接读字节**（node 遍历 CRLF/LF 计数）才戳破的，`--check` 的绿色输出完全不可信；
  2. 与 #7 是同一根因的不同表现：#7 是"文件检查了但内容被翻转"，#10 是"新文件压根没进检查名单"。
     **#7 的防复发机制（自动检查）本身带着 #10 的漏洞**，所以新项目的 EOL 检查要在**第一次提交前**就验证一次；
  3. 反向测试是发现这类问题最可靠的手段：故意让检查器该报错的地方出错，看它是否真的报错。
     本次新增的 `check-webview-client.mjs` 就做了负向测试并确认 exit 1。
- **验证**：修复后 `normalize-eol.mjs` 报出并修正 25 个文件；`--check` 全部 CRLF；
  `check-registry.mjs` 五节全绿。

## 11. webview 内联客户端代码放在模板字符串里 → 反引号与反斜杠是两颗地雷

- **日期**：2026-09-23（Chat 面板重写 Phase 2 编写 `src/ui/chat/html/client/*.ts` 时踩中，CUSTOM-20260923-011）
- **现象**：`boot.ts` 与 `toolCallView.ts` 编译报 `TS1005: ',' expected`，位置指向文件中部**看起来完全正常**的一行：
  ```
  src/ui/chat/html/client/boot.ts(62,33): error TS1005: ',' expected.
  ```
  该行内容是 JSDoc：`` * yet. Round-tripping keeps `marked` out of the webview bundle ``
- **根因**：客户端 JS 是**嵌在 TS 模板字符串**里的。模板字符串内部的**反引号**（哪怕在注释里）
  会直接终止字符串，后续内容溢出到 TS 语法层；而 tsc 的报错位置在溢出点附近，与真正的
  肇事处（注释里的反引号）相距甚远，定位成本高。
- **第二颗地雷（未踩中但同源）**：想出现在**生成脚本**里的反斜杠必须双写——
  源里写 `'\n'` 会在生成脚本中变成真实换行（语法错误），必须写 `'\\n'`；
  `\uXXXX` 转义同理，且容易写成非法值——本次差点写了一个 `\u` 后跟 5 位十六进制的转义
  （表情符号的码点超出 BMP），而 `\u` 只吃 4 位，多出的那个字符会变成字面量。
  最终改用 BMP 内的符号规避。
- **解法**：新增 `CUSTOMIZATIONS/scripts/check-webview-client.mjs`，
  抽出各客户端模块的模板内容 → 按 `index.ts` 顺序拼接 → 交给 `new Function(source)` 做
  **语法校验**（只解析不执行）。已接入 `check-registry.mjs` **§5**，因此 CI 会跑。
- **约定**：客户端模块内的注释一律用 `'单引号'`，**禁用反引号**；
  头部注释里必须保留"反斜杠要双写"的提醒（`dom.ts` 等文件已写）。
- **复发记录**：2026-09-30（CUSTOM-20260930-143）在 `styles.ts` 的注释里又写了一次
  `` `disconnected` `` —— `tsc` 立刻报 TS1005（模板字符串提前结束）。**闸门是有效的**，
  没有流出去；但这条要**在写注释的那一刻**过一遍，而不是写完再想：模板体里（含注释）
  只认单引号和中文引号。
- **教训**：
  1. **"能编译"和"生成的脚本能跑"是两回事**——tsc 只看 TS 层，看不到拼接后的产物。
     凡是"把代码当字符串拼起来"的设计，都要有一条对**产物**而非**源**的校验；
  2. 报错位置离谱时，先怀疑**字符串边界**（引号/反引号/转义），而不是那一行的语法；
  3. 新增检查器必须做**负向测试**（本次注入了带真实换行的字符串，确认报 `[SYNTAX]` 且 exit 1）。

  负向测试确认能检出并返回 1；`check-registry.mjs` 五节全绿。
- **复发史（同一颗地雷踩了四次，四次升级的方向不一样——这一节比上面的"解法"更值得读）**：

  | 次 | 何时 / 哪个 change-id | 踩的是什么 | 得到的教训 |

## 12. 工具写入字面控制字符（NUL）→ 文件被 `grep` 当二进制，搜索静默失效

- **日期**：2026-09-23（Chat 面板重写 Phase 2 写 `ChatPanelHost.ts` 时发生，CUSTOM-20260923-011）
- **现象**：`grep -rn "active-session-changed" src/` 的输出里出现
  ```
  Binary file src/ui/chat/ChatPanelHost.ts matches
  ```
  文件里既没有二进制内容，也没有刻意写入控制字符。
- **根因**：写文件时把一个**转义序列当成了字面字符**——想在注释里表达 `\0` 分隔符，
  实际落盘的是真实的 0x00 字节。事后逐字节扫描确认该文件有 2 个 NUL。
  同一轮里 `check-registry.mjs` 也中招：想写"匹配控制字符的正则"`/[<控制字符>]/`，
  结果正则里嵌进了真实控制字符，**检查脚本自己成了被检查的对象**。
- **危害**：不像语法错误那样立刻失败，而是**静默降低所有后续搜索的可靠性**——
  grep / ripgrep 默认跳过二进制文件，人和 AI 都会以为"这个文件里没有那个符号"。
  这是最坏的一类故障：工具返回"没找到"，而事实是"根本没搜"。
- **解法**：`check-registry.mjs` 新增 **§6 源码卫生**，逐字节扫描 `src/` 与
  `CUSTOMIZATIONS/scripts/`，命中即报 `[CTRL-BYTE] <file>:<line>: 0x<code>`。
  实现上**按码点判断**（`code === 0 || code < 9 || (code > 13 && code < 32)`），
  而不是嵌字面控制字符的正则——否则检查脚本会重蹈覆辙。
- **教训**：
  1. **"grep 说没有"不等于"没有"**——看到 `Binary file ... matches` 必须先查为什么是二进制，
     而不是换个关键词再搜；
  2. **检查器本身也要遵守它检查的规则**（本次两者同时中招，很有说服力）；
  3. 写"关于控制字符的代码"时，永远用码点/转义，不要用字面量。
- **验证**：`node CUSTOMIZATIONS/scripts/check-registry.mjs` 的 §6 报「(无控制字符)」；
  修复前该节会报出 `ChatPanelHost.ts:42: 0x00`（已实测）。

- **复发记录（2026-09-24，CUSTOM-20260924-026）——这次是"正确的转义写法"也不安全**：
  要写一个"这段文本是不是空白"的判据，需要把**零宽字符**（U+200B..U+200D / U+2060 / U+FEFF）
  也排除掉（它们**不在** `trim()` 的范围内，但视觉上完全不可见）。我按本条的教诲**没有贴字面量**，
  而是写转义 `​`……**结果落进源码的是真字符**：工具链的内容参数会经过一层转义解析，
  `\uXXXX` 在这一层就被还原了。
  换第二条路：写个 node 脚本"按码点定位再替换"，**又踩了另一个坑**——`node -e "..."` 里
  双引号会吃掉一层反斜杠，`\s` 变成了 `s`，正则被改成 `[s…]`，**会把含字母 s 的文本判成空白**
  （一个比原 bug 更隐蔽的错误：判据本身错了，而检查器只看语法）。
  最终解法：**按码点判断，源码里一个反斜杠都不出现**——
  ```ts
  const BLANK_CODES = new Set([0x200b, 0x200c, 0x200d, 0x2060, 0xfeff]);
  for (const ch of text) {
    if (BLANK_CODES.has(ch.codePointAt(0) ?? 0)) { continue; }
    if (ch.trim().length === 0) { continue; }
    return true;              // 有可见字符
  }
  return false;
  ```
  **教训升级**：
  1. **"用转义而不是字面量"这条纪律本身不够**——只要代码要穿过一层字符串转义（工具参数、shell、
     模板字符串），`\uXXXX` 就可能在任何一层被还原。**判据类代码优先避开转义**：
     码点数组 + `String.fromCharCode`/`codePointAt` 是最稳的形态；
  2. **改完必须直接读字节复核**（本次是靠读源码行确认"不可见字符还在"才发现的），
     语法检查、lint、类型检查**都看不见这类错误**；
  3. **shell 里的 `node -e "..."` 是第三层转义陷阱**：涉及反斜杠的脚本请写成文件再跑，
     或者干脆让脚本自身不含反斜杠。

## 16. 用 `textContent` 判断"有没有内容"是错的 —— 隐藏/裁剪的元素照样有 textContent

- **日期**：2026-09-25（CUSTOM-20260925-036，排查"重开 session 后全是白条"时自己踩的）
- **现象**：为查一个"界面看起来是空的"的 bug，写了个诊断：遍历条目、`textContent` 为空的比例过半就报警。
  **它一次都没报**，而用户明明看到一片空白。于是又白跑了一轮排查。
- **根因**：`textContent` 是**文档树里的文本**，与"渲染出来了吗"无关。元素被 `display:none`、
  `visibility:hidden`、被 `overflow:hidden` 的祖先裁剪、或自身高度塌成 0 时，`textContent` **依然有值**。
  而当时要抓的恰恰就是"文字在 DOM 里但没显示出来"这一类。
- **解法**：判"有没有显示"要量几何或看计算样式——本次改成
  `getBoundingClientRect().height < 6` 作为"这条渲染成了一条白条"的判据，
  并把 `getComputedStyle` 的前景/背景色一并 dump 出来（"文字色＝背景色"这类纯视觉故障，
  任何基于文本内容的判据都看不见）。
- **顺带的产品教训**：**报障描述与真实故障可能相差很远**。"没有内容"（用户语）与"内容存在但不可见"
  在文本层面完全一样，但在排查方向上完全相反（一个查数据链路，一个查样式/布局）。诊断必须能区分二者，
  否则它会用"没报警"给出一个假结论。
- **验证**：白条复现时诊断会给出 `kind h=… txt=… fg=… bg=…` 一行；`txt` 大而 `h` 小即命中本条。

## 17. column flex 容器 + 子项 `overflow: hidden` → 子项被**压扁**而不是让容器滚动

- **日期**：2026-09-25（CUSTOM-20260925-037，定位"整屏白条"的真根因）
- **现象**：一个 207 条的会话，工具卡全部渲染成**2px 高的白条**（只剩两条 1px 边框），
  用户描述为"全是白条没有内容"。而用户气泡、plan 卡片显示完全正常。
- **诊断指纹**（这次是日志直接给出的）：
  ```
  user h=31 txt=24  vis=visible     ← 正常
  tool h=2  txt=201 vis=visible     ← 白条：文本在、可见性正常，但高度 2px
  ```
- **根因**：`.messages` 是 `display: flex; flex-direction: column; overflow-y: auto`，
  而 CSS Flexbox 规范规定：**flex 子项的「自动最小尺寸」（`min-height: auto`）在其 `overflow`
  不是 `visible` 时等于 0**。工具卡 `.tool` 正好有 `overflow: hidden` ⇒ 失去最小高度保护 ⇒
  内容一超出容器，flex 按比例把它们**压扁**（206 张卡挤进 ~500px → 每张 2px），
  内容被 `overflow: hidden` 裁掉，**容器的 `overflow-y: auto` 永远不会触发**。
  没有 `overflow` 的子项（用户气泡 / plan 卡）自动最小尺寸 = 内容高度，压不动，
  所以同一屏里"有的正常有的空白" —— 这个**混合指纹**是判断本条的最快入口。
- **解法**：`.messages > * { flex: 0 0 auto; }`（禁止收缩），溢出交给容器滚动。
- **为什么"重开才坏"**：新会话条目少、总高不溢出 ⇒ 从不触发；老会话条目一多 ⇒ 立刻全压扁。
  **`overflow-y: auto` 看着像"已经处理了溢出"，但它管不了 flex 收缩**——这是本条最反直觉的地方。
- **教训**：
  1. **`display: flex` 的滚动容器，子项默认会被压缩**。凡是"flex + overflow"的容器，
     都要问一句"子项该不该缩"。对照：本仓库 `.tab-strip` 是同样的结构，但子项早就写了
     `flex: 0 0 auto`，所以从没出过这个问题——**同一个坑，写的时候想到就没坑**。
  2. **"界面是空的"先量高度，别先怀疑数据**。本例中 `textContent` 有 201 个字符、
     `visibility` 正常、`color` 与背景也不同——所有"内容层面"的检查全部通过，
     唯一异常的是几何尺寸。**用内容指标去查布局故障，方向就是错的**（见 #16）。
  3. 报障语言与真实故障之间可能有很大距离："没有内容"实际是"内容被压成 2px"。

## 13. `hidden` 属性被作者样式表的 `display` 声明覆盖 → 元素永远可见

- **日期**：2026-09-23（Chat 面板新面板首次 F5 验收时发现，CUSTOM-20260923-017）
- **现象**：打开一个 session 后，遮罩「Loading session history…」**一直不消失**。
  但**遮罩后面的内容其实已经完整渲染**（Markdown 表格、代码块、工具卡片全在）——
  说明加载是成功的，问题在遮罩本身。更严重的是遮罩是 `position: fixed; inset: 0; z-index: 40`，
  **同时吞掉了整块面板的点击**，输入框和发送按钮都用不了。
- **根因**：`hidden` 属性**不是**一个"魔法属性"，它依赖浏览器默认样式表里的
  `[hidden] { display: none }`。而**作者样式表里的任何 `display` 声明都会覆盖它**——
  这与选择器权重无关，是「作者样式 > UA 样式」的层叠顺序决定的（`*`、类选择器、id 选择器都一样）。
  所以凡是 CSS 里写了 `display: flex` 的元素，`hidden` **完全失效**。

  本仓库中招的三个（都已核对）：
  | 元素 | 冲突的规则 | 症状 |
  |---|---|---|
  | `#loadOverlay` | `.load-overlay { display: flex }` | 常驻可见 + 吃掉全部点击 |
  | `#agentBar` | `.agent-bar { display: flex }` | 只有一个 agent 时也显示一条空条 |
  | `#attachments` | `.attachments { display: flex }` | 没有附件时也占一段空隙 |

- **解法**：加一条全局规则把 `[hidden]` 的语义抢回来（`!important` 保证压过后面的类规则）：
  ```css
  [hidden] { display: none !important; }
  ```
  位置在 `src/ui/chat/html/styles.ts` 的 `<style>` 顶部，注释里写明了"不要删"的理由。
  **不需要改任何 JS**——现有的 `.hidden = true/false` 赋值在规则生效后就是对的。
- **为什么静态检查完全看不出来**：tsc / ESLint / webpack / 单元测试都不模拟 CSS 层叠。
  「作者样式覆盖 UA 样式」是**只有真实渲染才会暴露**的行为。
  **这是"静态检查全绿 ≠ 界面能用"的典型样本**——本次首跑一共只发现这一个 bug，
  而它是一个纯 CSS 层叠问题。
- **教训**：
  1. **`hidden` 只在一个元素没有任何 `display` 声明时才可靠**。要控制显隐，
     要么确保 CSS 里不写 `display`，要么用显式类切换，要么像这里一样用 `!important` 兜底；
  2. 排查"元素不消失"时，**先看它背后是不是真的没数据**——本例中内容其实已经渲染好了，
     只是被盖住，这个观察直接把范围从"加载逻辑"缩到了"遮罩显隐"；
  3. 用 `hidden` 的元素如果同时需要 `display: flex/grid`，就是一颗定时炸弹——
     加 `display` 的那一刻它会静默失灵。
- **验证**：`npm run compile` 后宿主窗口 `Ctrl+R`；打开 session 时遮罩在加载完成后消失、
  加载期间正常出现；只连 1 个 agent 时顶部无空白条；无附件时输入框上方无多余空隙。

## 14. 待决的 `session/request_permission` 不回答 = agent 永久挂起（而且完全静默）

- **日期**：2026-09-24（做面板内权限卡时**读 SDK 契约**发现，CUSTOM-20260924-020）
- **性质说明**：这条不是踩出来的，是读代码读出来的——但它一旦发生，现象是"agent 不动了"，
  没有报错、没有日志、没有超时，定位成本极高，所以提前记下。
- **契约**：ACP 的 `session/request_permission` 是一个 **JSON-RPC 请求**，客户端必须回答。
  SDK 文档注释明确要求：**会话被取消时，客户端必须把每个待决的权限请求以
  `{ outcome: 'cancelled' }` 结束**；而 SDK 侧**没有任何超时**（`grep setTimeout` 在权限路径上零命中）。
- **上游实现的缺口**：`SessionManager.cancelTurn` 只发 `session/cancel`，从不解决那个 promise；
  `PermissionHandler` 的 QuickPick 又带 `ignoreFocusOut: true`，会一直挂着。
  在"只有弹框"的年代这个缺口表现不明显（用户总能在弹框里点一下），
  一旦把提示搬进面板就会立刻显形：卡片点不了（面板关了、或切到了别的会话）而 agent 在等。
- **解法**（三处，缺一不可）：
  1. `SessionManager.cancelTurn` 的**第一句**就 `permissionBridge.cancelSession(sessionId)`，再发 `session/cancel`；
  2. `session-closed` 事件接同一个方法（会话关闭 / agent 退出）；
  3. 面板最后一条 surface 断开时 `ChatPanelHost.detachSurface` 调 `bridge.onPresenterLost()`，
     把面板卡片降级为 `deferred` 并入队弹框——**这是"agent 不挂死"的最后一道保险**。
- **教训**：
  1. **"有没有超时"是这类集成问题的第一问**。没有超时 = 每条异常路径都必须显式回答，
     不能指望"用户总会点一下"；
  2. 这类缺口只在**把 UI 从"永远在场"改成"可能不在场"**时暴露。搬 UI 时问一句：
     这个 UI 消失时，谁在等它？
- **验证**：待决时按 Stop/Escape → 卡片变 `Cancelled`，`ACP Traffic` 里 `session/cancel` 之后
  agent 返回 `stopReason: cancelled`（而不是继续等待）。

## 15. 「只能打补丁、不能重建」的渲染函数 → 任何"先落地后补数据"的路径都留下永久空壳

- **日期**：2026-09-24（CUSTOM-20260924-027，用户反馈「工具调用的记录好像没有显示」）
- **现象**：对话里工具调用的位置只有**一个带边框的空框**（`.tool` 空壳），点不开、没有工具名、
  没有状态图标。用户描述为"没有显示"——因为空框看起来就像一条空行，不像"卡片渲染失败"。
- **根因（分两层）**：
  1. 客户端 `place()` 在没有 view model 时会渲染一个占位空壳（代码里有 `console.warn` 提示）；
  2. **修复只做了一半**：018 给 `append()` 加了「发现是空壳就整卡重建」的分支，
     但**没给 `updateTool()` 加**。而工具跑起来后绝大多数消息是 `tool_call_update` → `updateTool`，
     它调的 `toolCallView.update` 只能改 `.tool-status` / `.tool-title` / `.tool-body` 三个 span，
     **永远修不了一个没有 `.tool-head` 的空壳**。于是只要卡片第一次落地时没带上 view model，
     后续所有更新都修不了它——018 的注释甚至写明了这一点（"a shell used to be permanent.
     Rebuild instead."），但只改了两条路径里的一条。
- **解法**：① `updateTool` 补同样的重建分支；② **别再赌数据在哪一侧丢**——客户端渲染占位卡的同时
  发一条 `needToolView`，扩展侧（`resendToolView`）把视图模型定向送回，自愈；
  ③ 索引里真的没有时记日志（原来只有 webview console 的一条 warn，输出通道里什么都看不到，
  这是"查不出来"的主要原因）。
- **教训**：
  1. **同一个渲染函数有两条入口（首次 append / 后续 update）时，修复必须同时覆盖两条**。
     只修一条的表现是"有时好有时坏"，而"有时好"恰恰让人以为问题在数据侧。
  2. **"查不出来"往往不是线索少，而是线索没进你能看的地方**。webview 的 `console.warn`
     需要手动开 Webview DevTools；把它变成扩展侧日志（哪怕只是转发一行），定位成本差一个量级。
  3. **占位元素要"看起来像出错了"，不能"看起来像没内容"**。空框被误读成空行，导致报障描述
     与真实故障相差很远。占位至少要有标题（哪怕就是 id）与说明文字。
- **复发记录（2026-09-25，CUSTOM-20260925-040）**：同一个教训的**第二次**——这次是工具卡的 body。
  形态略有不同：不是"修了一条路径忘了另一条"，而是**一开始就写了两份构建**。
  两份的差异本身就是缺陷：`render()` 会渲染 `locations` chips，`update()` 从不渲染、还会
  `NS.dom.clear(body)` 把首屏已渲染的 chips 清掉；`renderDiff` 每次以 `body.hidden = true` 新建，
  于是用户刚展开的 diff 被下一次更新合上（而正在跑的命令每个输出分片都会推一次 `tool_call_update`）。
  **这次的解法比"记得改两处"更彻底**：抽出 `fillToolBody(body, tool)`，让两条路径**共用同一份构建**——
  把"必须同时改两处"这种纪律换成**结构上只存在一处**。
  **教训升级**：同一个渲染器有多条入口时，不要靠"记得都改"来维持一致，要把它们收敛成同一个函数。
  **纪律会被忘记，结构不会。**

## 18. 同一个值在"协议层"和"记录层"各叫一个名字 → patch 被静默丢弃

- **现象**：Claude Code 的 Todo 列表（ACP `plan` 通知）在面板里**永远停在第一次快照**；
  切到别的会话再切回来，又正确了。
- **为什么"切走再切回是对的"是定位的钥匙**：两条路径读的是**不同的东西**——实时更新走
  `revise` → 客户端 `patch()` 按 `PATCH_KEYS` 把值拷进 entry；切换会话走**完整 snapshot**
  （`hydrate`），直接读记录里的真实字段。**一条路径错、另一条对**，说明缺陷在增量路径上，
  而不在数据本身——这条推理比任何静态检查都先一步缩小了范围。
- **根因**：同一个值在两层各有一个名字。
  | 层 | 名字 |
  |---|---|
  | 协议（`EntryPatch`） | `plan` / `content` |
  | 记录（`PlanEntryRecord` / `ContentEntry`） | `entries` / `blocks` |
  客户端 `PATCH_KEYS` 照抄的是**协议层**的名字，于是 `patch()` 把新值写进了 `entry.plan`，
  而渲染函数 `buildPlan()` 读的是 `entry.entries`。`patch()` 对**不认识的键不报错**——
  它只是把键拷进对象，当作什么都没发生。
- **教训**：
  1. **替换型 patch 的键名必须与被替换的字段名逐字相同。** 记录字段叫 `entries` 就写 `entries`，
     不要为了"更贴协议"另起一个名字——两层各叫各的，错位只是时间问题。
  2. **这是字符串字面量错配，编译器不检查。** `tsc` / `eslint` / webpack / `check-webview-client.mjs`
     **全都看不见**（同 pitfall #2、#4 的家族）。改协议字段名时唯一可靠的办法是 `grep` 出全部消费点
     逐一对照（本次即 `types.ts` / `TranscriptStore.patch` / `ChatPanelHost` 的 plan 分支 /
     客户端 `PATCH_KEYS` 四处）。
  3. **"拷贝式"的 patch 对未知键静默，本身是好防御**（防止未来的消息形状污染 entry），
     但它把"拼错名字"从"崩溃"变成了"永远不生效"。这类静默只能靠**命名一致**避免，测试测不到。
- **防复发**：`EntryPatch` 的注释里写明"键名 = 记录字段名"，客户端 `PATCH_KEYS` 上方同样标注互指。
  同轮把 `content` 那条（同样错位、但当时没有调用点）一并改掉——**潜伏的同源错误要顺手清掉**，
  否则下次有人加 `patch.content` 时会再踩一遍，而且更难查（新代码会被怀疑，旧字段名不会）。
- **来源**：CUSTOM-20260925-038（面板审计阶段 1）。

## 19. 同一份知识在"宿主"和"客户端"各存一份 → 迟早只改一边

- **现象**：不是一次故障，是一个**反复出现的漂移温床**。面板审计（阶段 1）清点出两处：
  | 知识 | 宿主侧 | 客户端侧 |
  |---|---|---|
  | 工具状态字形 / kind 标签 | `content/toolCalls.ts` 的 `statusGlyph`/`statusClass`/`kindLabel` | `html/client/toolCallView.ts` 顶部的 `STATUS_GLYPH`/`KIND_LABEL` |
  | agent 名字面量 `'Claude Code'` | `panelContract.MODERN_AGENTS`（面板路由）、`NestingStrategy`（嵌套策略）、`AgentConfig`（排序） | `html/client/sessionMenu.ts` 的 `CONNECT_LABEL`（硬编码字符串） |
- **为什么危险（不是"重复代码不好看"这种层面）**：宿主与客户端是**两个独立的代码世界**——
  客户端代码是模板字符串里的 JS，跨不过类型检查、也没有任何自动检查能比对两边。
  所以"改了一边"这件事**不会有任何东西告诉你**。038 就是同一族的一个真实实例：
  协议层与记录层各叫一个名字，结果更新被静默丢弃，而四个自动检查全绿。
- **本轮的处理（刻意不是"合并"）**：
  1. `statusGlyph` 那三份**保留**，但在文件头写明「**改一处必须改另一处**」并点出它与 038 同源。
     真正合并需要一个**协议变更**（把 glyph/label 随 `ToolCallView` 一起下发）——那是独立一轮，不是顺手能做对的事。
  2. 客户端那份同样在常量旁互相指认。
  3. `sessionMenu.ts` 的硬编码标签**当时就承认了**（注释里写了"如果有第二个 modern agent，
     这个字符串应该由宿主下发"），本轮保留该注释。
- **教训**：**判断这类重复危险不危险，看的是"两边能不能互相发现"**。
  同一个文件里重复两份没关系（读代码时必然同时看到）；**跨宿主/客户端、跨语言、跨构建边界**的重复，
  就必须要么加注释互指、要么让其中一侧成为唯一真源（走协议下发）。
- **来源**：CUSTOM-20260925-052（面板审计阶段 4）。

## 20. 设计预留但从未接线的 CSS → 以后一定被当成 bug 反复排查

- **现象**：`styles.ts` 的 `.tab-dot.attention` 是**完整实现的一条样式**（蓝色小圆点），
  但**全仓库 grep 只命中它自己**——没有任何 JS 会加 `attention` 类。它像"没接完的功能"，
  而看代码的人只能靠"找不到调用方"来推断这一点，心里没底。
- **为什么值得单独记**：这类残留会**主动制造排查成本**。下一个看到"后台会话在等你"这个需求的人，
  会先花时间确认"这个类是给谁用的、为什么没生效"——而答案是"从来没接线"，
  这条信息**只存在于某个人的记忆里，不在代码里**。
- **本轮的处理（保留 + 写明）**：用户明确决定**不做**那个功能（后台会话的权限提示改由窗口弹框承担），
  但样式**保留**（将来接线时不用重新想配色）。于是在它上方写明：
  意图是什么、为什么没接、**以及"看到它没生效别当 bug 修，先确认要不要做那个功能"**。
- **教训**：预留代码本身没错，**"预留"这件事必须写在代码里**。判断标准很简单：
  一句话能说清"它为什么在这里、谁负责接线"，就写那一句；说不清就该删。
  同轮的对照：`statusGlyph` 那三份保留时也写明了两件事——**谁会用**（将来的日志/树项）与
  **改动纪律**（改一处必须改另一处）。两条都是"删不掉的理由"，而不是"不舍得删"。
- **来源**：CUSTOM-20260925-052（面板审计阶段 4）。

## 21. 白名单放行整个 `data-*` 家族，而点击委托偏偏信任其中几个属性

- **位置**：客户端 `html/client/dom.ts` 的 `sanitize()` —— 属性白名单的判定是
  「**不在名单里、且不以 `data-` 开头**才删」，等于**放行全部 `data-*`**。
  而 `links.ts` 的点击委托信任的正是 `data-href` / `data-path` / `data-terminal` / `data-line`
  这几个 data 属性（它们决定"点一下会发生什么"）。
- **当前不可利用**（这是本轮**没有**把它升级为紧急项的理由）：唯一进入 `sanitize()` 的内容来自
  宿主侧 `SafeMarkdown`，而它的 `html()` 钩子把原始 HTML **转义成文本**，
  因此没有任何路径能把标签注入进去。
- **风险在于未来**：`sanitize()` 的定位是**第二层兜底**——防的是"将来 marked 新增了没人覆盖的渲染钩子"。
  而恰恰在这种场景下，它**没有约束住自己最该约束的那几个属性**：一个被漏掉的钩子只要输出
  `<span data-path="C:\...">`，点击委托就会照单执行。白名单放行 `data-*` 的初衷是"data 属性无害"，
  但这个代码库自己**定义**了若干 data 属性为"可执行指令"。
- **教训**：**"通用地放行一类属性"和"具体地信任其中几个"不能同时成立**。
  兜底层要按"我会执行什么"来写白名单，而不是按"什么一般无害"。
  本轮只记录不改（当前无路径可达、且改动它需要同时调整 markdown 侧的产出契约）；
  真要动手时应把 `data-href` / `data-path` / `data-terminal` / `data-line` 从 wildcard 里**摘出来单独校验**。
- **来源**：面板审计（阶段 1）D 节；CUSTOM-20260925-052 期间复核确认仍成立。

## 22. 谓词的名字与它的实现相反 → 调用点做的事正好是注释说的反面

- **日期**：2026-09-25（`CUSTOM-20260924-026` 引入，`CUSTOM-20260925-055` 修复）
- **现象**：用户报「重新打开看到的会话有问题，跟实时看到的内容不一样」——实时视图正常，
  **重开后助手正文与 Thought 块全部消失**，而用户消息与工具记录都在。
- **根因**：`contentBlocks.isBlankText()` 的 `return true` / `return false` **写反了**。
  实测：`isBlankText('abc') === true`、`isBlankText('   ') === false`。
  调用点写的是
  ```ts
  // 意图：看不见就不建记录
  if (!merges && isBlankText(text)) { return null; }
  ```
  判据反了之后，它变成**「看得见就不建记录」**——每一个*新开一条记录*的真切正文分片被丢掉，
  空白分片反而被保留下来。
- **为什么它藏了一整天，而且四个自动检查全绿（这是本条最值得记的部分）**：
  1. **实时路径靠巧合是对的。** 实时流里 agent 会先发一个换行 / 空白分片当分隔符，
     按反了的判据它"不是空白" ⇒ 记录被建出来；之后真切正文走的是**合并**分支
     （`merges === true` 时那个守卫被整段跳过）⇒ 正文正常追加。
     **而 replay 是单块真切正文、前面没有空白分片** ⇒ 记录直接被丢。
     "实时好、重开坏"这个奇怪的不对称，全部来自这个巧合。
  2. **名字替代码撒了谎。** 它的名字（`isBlankText`）与**文档注释**
     （"True when this text would render as something the reader can see" ——
     这描述的恰好是**正确**极性）都是对的，只有函数体是反的。读代码的人会相信名字。
  3. **`''` 走的是提前返回。** `if (!text) return true;` 这个分支是**对的**，
     所以"空文本块"那条路径一直工作正常——**半个函数是对的，更看不出另外半个是反的**。
  4. **客户端的同名副本是对的。** `toolCallView.isBlank` 极性正确，于是"两边对照"也暴露不了它
     （对照的前提是知道哪边对）。
- **它是怎么被找到的（方法论，比 bug 本身更值钱）**：不是读代码读出来的，是**先拿到真实数据**——
  写抓包脚本用真实 agent 抓一份 `session/load` replay，**结论当场推翻了最初的假设**
  （以为"agent 不回放正文"，实际 replay 里两轮答案、markdown 表格、thought 全都在），
  再把夹具喂进可自动运行的宿主侧测试，一次就复现并定位。
  **顺序很重要：先拿到协议事实，再写断言。** 反过来会把自己的假设固化进夹具。
- **教训**：
  1. **谓词函数（`isXxx` / `hasXxx` / `shouldXxx`）值得配一条直接的单元测试**——
     它的错误形态就是"整体取反"，不报错、不崩、只是语义全反。
     本轮补的 `isBlankText polarity` 套件里，最强的一条是**用真实数据当判据**
     （夹具里每一条真实正文分片都不得被判为空白），而不是我编的用例。
  2. **调用点的注释要写意图，测试要写事实。** 本条的调用点注释（"看不见就不建记录"）
     清楚地记录了意图，正是它让"实现与意图相反"这件事**可被发现**——注释没白写。
  3. **"实时好、另一条路径坏"是一种强信号**，它几乎总是指向"某处依赖了某个巧合"。
     这里的巧合是"agent 实时会先发一个空白分片"。同类信号还有 022 那条
     （`refreshSessions` 每个 chunk 都跑，只是恰好被签名去重挡住）。
- **来源**：CUSTOM-20260925-055（面板审计后续；由 054 建的真实 replay 测试当场抓到）。

## 23. 数据更新被 UI 状态门控 → 用户的操作被静默丢弃

- **日期**：2026-09-25（`CUSTOM-20260925-058` 的第一次实现，`059` 修复）
- **现象**：草稿页里点「Browse…」→ 在系统文件夹对话框里选好目录 → 点「Use this directory」→
  **面板里显示的目录没有变**。没有任何报错、没有任何日志——看起来就像点击没生效。
- **根因（两处，同一个反模式）**：
  ```js
  function setChoices(message) {
    choices = message;
    if (!open) { return; }        // ← 抽屉关着就直接返回……
    if (draft && !draft.cwd) { NS.draft.setCwd(...); }   // ← 采用默认目录在这后面
  }
  function setPicked(path) {
    if (!open) { return; }        // ← 同样：抽屉关着就丢掉用户的选择
    ...
  }
  ```
  1. **草稿页出现时抽屉本来就是关的**（`focusDraft` 直接调 `refresh`，不经过 `show`）⇒
     「采用宿主给的默认目录」这一步**永远不会执行**，头部一直显示 `Default directory`。
  2. **系统文件夹对话框是会抢焦点的异步交互**——它的结果什么时候回来、那时我们的抽屉是不是还开着，
     完全不受我们控制。一旦不成立，**用户的选择被静默丢弃**。
- **为什么极难发现**：两条路径都**不报错、不崩溃、没有日志**。用户能描述的只有"点了没反应"，
  而"没反应"的可能原因太多（事件没绑上、消息没发出去、宿主没处理、返回没收到……）。
  本次是靠**用户截图里的那一行 `Default directory`** 才反推出第 1 条的——它暴露了
  "默认目录从未被采用"这个中间状态。
- **修法**：**数据更新不再门控于 UI 状态**——`setChoices` 无论抽屉开没开都采用默认目录；
  `setPicked` 无论抽屉开没开都应用结果（只在**需要重绘**时才看 `open`）。
  同时把抽屉里的草稿状态从"缓存一个 draft 对象"改成"只存 `draftId`、渲染时从 `NS.draft.get()` 现读"，
  消掉第二份真相（同族问题见 #19）。顺带删掉已经无用的 `browseIntent`（两个分支做同一件事）。
- **教训**：
  1. **问一句：「这个数据更新依赖某个 UI 状态吗？」** 依赖了就会在"该状态恰好不成立"时静默丢结果。
     判据：更新所依赖的应该是**数据本身的标识**（`draftId`），而不是"某个面板是否可见 / 是否打开"。
  2. **异步交互的结果不许依赖发起时的 UI 状态。** 需要"这次结果该作用于谁"，就用相关性 id
     （这里本来就为 `draftResolved/Failed` 设计了 `draftId`，却让**目录选择**走了另一条没有 id 的路）。
  3. **"点了没反应"类故障要在代码里留出声点。** 本次两处 `return` 都是静默的；即便修好了行为，
     也该在那两处留一行 `console.warn`（它会被日志桥送到输出通道，见 #15 的教训 2）。
- **来源**：`CUSTOM-20260925-059`（用户 F5 复验 058 时发现）。

## 24. 用常量偏移去对齐 → 必然错；锚到"已经在正确位置上的元素"才按构造正确

- **日期**：2026-09-25（`CUSTOM-20260924-023` 引入，`CUSTOM-20260925-061` 修复）
- **现象**：左侧引导条的圆点**统一偏上**，与右侧区块的首行对不齐（用户截图指出）。
- **根因**：`rail.measure()` 里是 `dot.style.top = (y + 6)`。CSS 用 `margin-top: -半高` 抵消尺寸，
  所以 `top` 就是**圆心**——于是圆心被钉死在"条目顶边 + 6px"这个位置。**而各条目首行的中心根本不在一处**：
  工具卡 `.tool-head` 有 3px 内边距（首行中心 ≈ 12px），用户气泡有 6px 内边距（≈ 15px）。
  一个常量不可能同时适配两者，**统一偏上 6–9px**。
- **为什么当初会写成常量**：写它的时候只看了一种条目（工具卡），量出来大约 6px 就写死了。
  这类错误的特征是——**它在作者当时看的那一种情况下是对的**，所以不会当场暴露。
- **修法（关键在于换一种"对齐的锚"）**：不再计算"首行中心在哪"，而是**锚到一个本来就在首行上的元素**——
  类型图标。`icons.attach()` 已经把图标放在该条目的首行上（它的 HOST 表把每种记录类型映射到内容宿主），
  所以**图标的几何中心就是要对的中心**。于是：
  ```js
  var anchor = node.querySelector('.rec-icon, .tool-icon') || node.firstElementChild || node;
  var rect = anchor.getBoundingClientRect();
  var centre = rect.top - origin + rect.height / 2;
  ```
  **没有常量、没有按类型分支，换任何新的记录类型都自动正确。**
- **教训**：
  1. **问一句：「这个偏移量是我量出来的，还是它本来就在那儿？」** 量出来的常量只对量它的那个场景成立；
     如果目标位置**已经由另一个元素体现**（图标、徽标、首行文本），就锚它——那是**按构造正确**
     （correct by construction），而不是**按测量正确**。
  2. **同一处的 CSS 负 margin 技巧要一起读**：`top` 到底是"顶边"还是"中心"，取决于 `margin-top` 是否是
     `-半高`。只读 JS 会得出错误结论（本次差点以为要改的是"加个更大的偏移"）。
  3. **同类征兆**：任何"看着差一点、调个数字就好"的常量，都值得先问上面第 1 条。
- **同轮的另一处相关教训（不是偏移，但同属"语义撞车"）**：引导条的"当前位置"用的是
  `box-shadow: 0 0 0 2px var(--vscode-focusBorder)`，而键盘焦点环用的是**同一个变量**（047 引入的
  `:focus-visible` 全局规则）⇒ **一个颜色两种意思**。改用**尺寸**（`transform: scale`）区分。
  **教训**：给一个视觉通道（颜色/环绕/尺寸/位置）赋予第二个含义之前，先确认它是否已经被占用了。

## 25. 用代码层面的信号去近似"用户看到的东西" → 判据必然漏一半

- **日期**：2026-09-26（`CUSTOM-20260925-061` 引入，`064` 修复）
- **现象**：用户报「多行用户消息也没有折叠」。而我读代码怎么看都对——多行确实会走 `<details>` 分支。
- **根因**：判据是 `text.indexOf('\n')`，即**逻辑换行**。但"多行"在日常生活中指**视觉上的多行**，
  而一条长句子会**自动折行**成一个换行符都没有的多行外观。用户看的是后者 ⇒ 判据根本没命中。
  代码里"是不是多行"与屏幕上"看起来几行"，**是两件事**。
- **为什么读代码发现不了**：因为读代码时我在验证"判据有没有被正确实现"（是的），
  而不是"判据是不是用户想要的那个问题"（不是）。**这一类错误在实现层面完全自洽。**
- **怎么定性（方法论，比 bug 本身值钱）**：写了一个**桩 DOM** 把客户端那段逻辑**真跑一遍**，
  三种输入一次就分清：单行短消息 → 不折（对）；**逻辑多行 → 折叠（对）**；**长单行 → 不折（错）**。
  **跑一遍比读十遍有效**——尤其当被测逻辑是纯函数式的时候，一个几十行的桩就够。
- **修法**：判据同时覆盖两种含义（`有换行` **或** `长度超过阈值`）。
- **教训**：
  1. **问一句：「这个判据对应的是用户看到的哪个现象？」** 只要答案里出现"大概/通常"，
     就该去找那个现象的**直接信号**（这里是"长度/渲染高度"），而不是拿一个更容易拿到的代理信号。
  2. **代理信号（proxy）的失败模式是不对称的**：它覆盖了 A 情况却漏了 B 情况，
     而作者当时测的往往正是 A（这里：我自己写的多行 fixture 都带真实换行）。
  3. **当"读代码查不出来"时，换手段而不是读得更仔细**：写一个能真跑被测逻辑的最小环境。
     本次的桩 DOM 只花了约 40 行，一次就定位——而此前已经读了好几轮代码。
- **顺带记**：同一个桩 DOM 后来长成了常驻测试（`068`），**并且它自己的假设也错了两次**
  （按"第一个子节点"取记录 → 假通过；只认"记录本身是 details" → 误判无折叠）。
  **测试替身的假设同样要被检验**——这就是测试代码也需要 review 的原因。

## 26. 把代理信号"调宽"不等于换成直接信号（#25 的第二次复发）

- **日期**：2026-09-26（`064` 修复后**仍然复发**，`071` 才真正修好）
- **现象**：用户 F5 复验 064 之后又报「多行的对话**还是**没有显示 fold 按钮」。
- **根因**：064 的修法是"判据同时覆盖两种含义：`有换行` **或** `长度 > 约 160 字`"。
  但那**仍然是一个代理**——它问的是"这段文本像不像多行"，而用户问的是"屏幕上占了几行"。
  窄侧边栏里一条 100 字、**一个换行符都没有**的消息会折成三行，却因为没到 160 字而不折叠。
  **阈值不是"更好的判据"，只是把这个代理的失效点挪远了一点。**
- **为什么"调宽阈值"看起来像修复**：它在作者当时试的那个宽度上确实好了（宽侧边栏里 100 字一行放得下）。
  这是 24 号坑"量出来的常量只对量它的场景成立"的同族错误，只不过量的是**阈值**。
- **修法（换成直接信号）**：不再猜——**先建出真正会渲染的结构，再量它**。
  行数用 `Range.getClientRects()` 数行盒（滤掉行长边界的零高矩形）；切分点二分 + 回退词边界。
  量不出来时（隐藏面板、无 `createRange`、超长）才回退旧判据，**并且只回退一次**。
- **教训**：
  1. **判据要从"用户看到的东西"里取，而不是从"我手里有的东西"里取。** 手边有字符串 ⇒ 先数字符；
     手边有 DOM ⇒ 才可能量行数。**先决定要量什么，再决定在哪一步量**（这里付出了"必须在插入 DOM 之后
     才能决定折叠"的结构代价，值得）。
  2. **测两个方向，才知道判据是"测量"还是"更宽的阈值"。** 071 的用例里，除了
     "只折行无换行 ⇒ 折叠"，还有一条"一行放得下的 200 字 ⇒ **不**折叠"——
     只有后者能排除"阈值调宽"这个解释。**一个只会朝一个方向失败的测试，什么都证明不了。**
  3. **同一个坑复发时，说明上一次的修法没解决它的类**。这次的结论写进 25 号坑的正文（代理信号），
     而不是只加一条新坑——**复发本身就是"它属于哪一类"的证据**。

## 27. 用"事件清单"去追布局变化 → 清单必然落后（而且落后的方式是静默的）

- **日期**：2026-09-26（`CUSTOM-20260924-023` 引入测量缓存，`070` 修复）
- **现象**：用户报「如果有内容块触发了 unfold，左侧引导线的圆点没有重对齐」。
- **根因**：圆点的 `top` 是**缓存**的，只在三个时机重算（标记集变化 / window resize / markdown 回填）。
  而让条目**高度**变化的原因有一堆：`<details>` 展开、工具卡正文展开（改的是 `hidden` 属性，
  它**根本不派发事件**）、图片加载完成……清单里一个都没有 ⇒ 圆点停在旧高度。
- **为什么没人发现**：漏掉的那几种情况都**不会报错**——dot 只是留在原地，
  而"留在原地"和"布局本来就没变"在代码里长得一模一样。
- **修法**：**别列清单，观察布局本身**——一个 `ResizeObserver` 观察每条记录节点，
  有任何尺寸变化就重测。它天然覆盖"以后新加的、我没想到的那种高度变化"，这正是清单做不到的。
- **代价与必要的边界**（不写下来下次就会被"优化"掉）：
  1. **回调要跳过仍在流式的记录**——否则每个 chunk 都触发全量测量，毁掉"流式期间零布局读取"这条既有性能设计；
  2. **只观察记录节点，不要观察 rail 自己**（那是观察自己的输出 ⇒ 回环）；
  3. **面板高度为 0 时不测量**（隐藏时所有几何都是 0，测出来的"真相"是错的）；
  4. **节点被替换的每一处都要重新挂**（替换后旧节点不再报事件，而新的没人观察）——
     这是唯一还需要"清单"的地方，所以它必须有注释说明漏了会怎样。
- **教训**：**"我枚举了所有情况"是一个应当被怀疑的断言**。凡是"某个东西变了但没有任何事件"的场合
  （CSS 改高度、`hidden` 属性、内容加载），都该用观察者而不是监听器。

**第三次复发（2026-10-03，`CUSTOM-20261003-176`）**：这次栽在**滚动状态**上，形态和 023 那次一模一样 ——
`pinned`（是否贴底）与 Jump 按钮只在 `scroll` 事件里更新，而"底部留白（输入卡/抽屉高度）变化"
和"内容被 markdown 撑高"**都不派发 scroll 事件**（改的是 padding / 子节点高度）。用户看到的是
"面板没到底、Jump 还挂着，但滚动条已触底、鼠标滚不动，最后一条还被浮层盖着"。
修法是**给状态一个显式的再计算入口**（`scroll.reflowNow()`），由"改了那个量的模块"主动喊一声 ——
清单仍然只有三处（三个写高度的模块），但它们**和那个量在同一处代码里**，不会像"事件清单"那样随
新功能漂移。教训补一句：**判断"要不要重算"的依据，应当是"那个量是不是我改的"，而不是"有没有事件"**。

## 28. 在点击处理器里重建 DOM → 之后那次点击会被"点外面"的检查当成点了外面

- **日期**：2026-09-26（`CUSTOM-20260926-079`，用户复验当场发现）
- **现象**：在换目录的下拉里**选中一个目录，整个「Previous session」列表跟着关掉了**。
- **根因**：点菜单项 → 抽屉的委托处理器把它当过滤器选项处理 → `applyFilter` **清空并重建菜单行**
  （把正在冒泡的那个按钮从 DOM 上摘下来）→ 事件继续冒泡到 `document` 上那个"点击别处就关闭"的监听器 →
  它问的是 `drawer.contains(event.target)` —— 而 **`contains` 对游离节点恒为 false** ⇒ 判定成"点了外面" ⇒ `close()`。
- **为什么读代码看不出来**：两个处理器各自都**完全正确**（一个重建列表、一个判断点是否在抽屉内），
  错的是**它们的先后顺序**加上"重建会摘掉 target"这条 DOM 事实。这种错误只在**真按派发顺序跑一遍**时才现形
  ——和 pitfalls #25 是同一类：**跑一遍比读十遍有效**。
- **修法**：问**派发时就定好的路径**，而不是事后去问"这个 target 现在在哪"：
  ```js
  var path = event.composedPath ? event.composedPath() : null;   // 派发瞬间固定
  if (path) { for (...) { if (path[i] === drawer) return; } }
  else if (drawer.contains(event.target)) { return; }            // 老环境兜底
  ```
- **怎么钉住它（这次的收获）**：给桩 DOM 补了**事件派发**——`addEventListener` 记录监听器、
  `dispatchClick(target)` 按「派发瞬间冻结路径 → target 先于祖先 → 最后 document」的顺序调用，并且
  **`stopPropagation` 真的会挡住 document**。四条断言里有一条是**反向的**（"点真外面仍然关闭"）——
  它保证修改没有把功能一起改没。**桩的忠实度由那条反向用例负责**：它一过，另外三条的失败就只能是产品的问题。
- **教训**：
  1. **任何"点击后重建自己"的交互，都不能用 `contains(event.target)` 判断点击位置**。同理适用于
     `document.elementFromPoint`（几何也变了）、以及任何"事后去问 DOM 现在长什么样"的检查。
  2. **写这类交互时问一句：「我处理完这次点击之后，target 还在原来的位置上吗？」** 不在，就要用派发期信息。
  3. **同一个模式在同目录下的 `directoryMenu.ts` 里没出问题，纯属巧合**——它选完目录本来就要 `close()`。
     **不要因为"那边一直没事"就以为这个写法是安全的。**

## 29. "没变化就不回话"的幂等请求 → 客户端的表现可以永远和宿主不一致

- **日期**：2026-09-27（`CUSTOM-20260926-080`，用户截图反馈）
- **现象**：从会话 A 切到一个**草稿页**（"New Session"），再点 A 的标签**毫无反应**，界面停在草稿页。
- **根因**：客户端点标签只发一条 `focusSession`，**渲染完全依赖宿主的 `focus` 应答**；
  而宿主 `case 'focusSession'` 调 `SessionManager.focusSession()`，后者**在"已经是这个会话"时 early-return**
  （设计上只在**变化**时 emit —— 对"状态同步"是合理的优化）。
  问题在于：**客户端的"我在看什么"不是宿主状态的函数**。草稿页是客户端私有的（058，宿主不知道它存在），
  于是宿主那边"我这边已经是 A 了" ≠ 客户端"我在草稿页上"⇒ 请求发出去了、也过了校验，只是**没人回话**。
- **为什么看不出来**：三个部件各自都符合自己的契约——客户端的"发请求等应答"、manager 的"变化才广播"、
  宿主的"转发请求"。**没有人写错，缺的是一条"这个请求必须被回答"的约定**（两边对"状态"的假设不同）。
- **修法**：宿主对**显式请求**用 `focusSession(sessionId, { force: true })` ——
  manager 自己早就为"用户可见的聚焦动作"准备了这个开关（`newConversation` / `loadSession` / `resume` 等
  5 处都在用）。**修在宿主而不是客户端**：客户端有两个调用点都有这个洞，
  而且**没有应答它根本没法渲染那条会话**（transcript 按会话存在宿主侧）——各自打补丁就是两份知识（#19）。
- **教训**：
  1. **问一句：「这个请求的应答，客户端能不能靠别的途径得到？」** 不能，就必须无条件回话，
     哪怕发起方要的东西**看起来**和现状一样。"幂等"说的是**效果**幂等，不是**可以沉默**。
  2. **凡是"以某一边的状态为真相"的优化（去重、跳过无变化的广播），都要问「另一边的状态能不能和它不同步」**。
     能（草稿、本地编辑、乐观更新、另一个窗口），这条优化就不成立。
  3. **反向守卫也要写**：这次同时钉住了"未知会话的聚焦请求仍然被丢弃"——
     否则"无条件回话"很容易被后人改成"无条件相信客户端"。

## 30. 把「我手里没有这个信息」读成「这个东西不存在」→ 报了一个把责任推给对方的错

- **日期**：2026-09-27（`CUSTOM-20260926-083`，用户截图提问）
- **现象**：还没连接任何 agent，历史选择器**列得出会话**（"3 sessions · from the local cache"），
  但点开每一条都弹 `Agent "Claude Code" does not support loading or resuming sessions.`
- **根因**：`session/load` / `resume` 的能力**只能从 ACP 的 `initialize` 握手里知道**，
  而 `openExistingSession` 读的是 `getCachedCapabilities()` —— **从没连接过 ⇒ 缓存是空的 ⇒
  `caps?.load` 与 `caps?.resume` 都是 undefined ⇒ 落到那句"不支持"**。
  缓存为空表达的是"我还没问过"，代码却把它当成了"对方回答说不支持"。**把未知当成了否定。**
- **为什么没人发现**：这条路平时都是"先连接、再点历史"，缓存自然有值；而**离线可读的列表**
  （本地缓存是为了"不 spawn 进程也能看历史"）恰好造出了"列表在、能力不在"的组合 ——
  两个各自正确的设计撞在一起。
- **修法**：读能力**之前**先按需连接（`ensureConnected` 幂等、并发合并，正是树视图"未连接时探测能力"用的原语）。
  **修在唯一决策点而不是两个调用方**（面板的历史选择器 + 树的 `acpc.openSession`）。
- **教训**：
  1. **三态，不是两态**：能力有"支持 / 不支持 / **还不知道**"三种状态，而 `caps?.load` 这种写法把后两者合并了。
     凡是"要问过才知道"的信息，都需要一个显式的"未知"分支——用 `undefined` 兼任"未知"是最常见的写法，
     也最容易在判空时被顺手当成"否定"。
  2. **错误信息会替代码背锅**：这句话把"我还没握手"说成了"你的 agent 不支持"，
     用户只能去怀疑 agent（而它明明支持）。**报错前先问：这句话对用户是"可行动的"还是"误导的"？**
  3. **反向守卫要写**：真正不支持的 agent 仍然必须报错——否则"按需连接"会被后人改成"连上就当支持"，
     把一个明确的错误变成一次静默失败。

## 31. 关于浏览器行为的"合理推断" → 布局这种事只能量，不能推

- **日期**：2026-09-29（`CUSTOM-20260929-114` → `115` → `116`，同一个功能上连续翻车两次）
- **现象**：
  - `114` 给助手消息加了折叠，但折叠后**看不到首行**（用户："折叠后文字看不到了"）；
  - `115` 用 flex 把正文首行挪到图标行，结果**把两个状态搞反了**：展开时首行跑到了图标行、
    折叠时一片空白（用户："搞反了"）。
- **根因**：两次都在**推断浏览器行为**，而且两次推断都自洽、都写在注释里当成了事实：
  1. 「作者样式优先级高于 UA 样式 ⇒ 我可以给正文写 `display`，覆盖 details 折叠时对非 summary
     子节点的隐藏」——**覆盖不了**。折叠态那片空白就是它。
  2. 「`display:flex` + `flex-wrap:wrap` + `flex-basis:100%` ⇒ 正文会换到第二行、与标题行同处一行
     只在折叠时发生」——**不成立**。`display:flex` 挂在 `<details>` 上并不产生"两个 flex 项目"的布局，
     实测是首行贴着图标走、其余照旧另起。
- **为什么读代码/推规范发现不了**：这两条都是**布局**问题，而本项目早就把边界写清楚了——
  桩 DOM 只测逻辑、测不了布局（`dev-workflow.md` 的分区表、`chat-client.test.ts` 的文件头）。
  我仍然用"读规范 + 经验"代替了"量一次"，于是把两个错误假设写进了注释，还在汇报里请用户 F5 验证。
- **解法**：`CUSTOMIZATIONS/scripts/preview-records.mjs`——把 webview **真正用的** CSS（`styles.ts`）、
  标记（`body.ts`）与全部客户端模块抽出来拼成一个独立 HTML，交给本机 Chrome/Edge **无头截图**
  （`#expanded` / `#collapsed` 各一张）。它复用生产代码、不复制任何知识（不是 pitfall #19 那种第二份拷贝）。
- **教训**：
  1. **布局问题必须量**：第一次跑这个脚本，两个状态的真实样子一次就出来了，而且**与两次推断都不一样**。
     之前两轮"推理 → 写代码 → 请用户 F5"的成本，远高于这 100 行脚本。
  2. **「抢样式」是最脆的一类修法**：任何依赖"作者样式能覆盖 UA 行为"的地方，先假设它会失败，
     去找**不依赖覆盖**的结构——`116` 的解法（把预览文本放进 summary，折叠时的隐藏交给浏览器自己保证）
     之所以对，是因为它**没有跟浏览器抢任何东西**。
  3. **一个自我检查信号**：当我在回复里写"请你 F5 看一眼 X"时，先问一句「我自己能不能看到 X」。
     这次答案是能（无头 Chromium），代价只有一个脚本；而看不到的那些（真实主题色、字体度量、
     VS Code 自身的布局）才该留给用户。

## 32. 「官方插件能弹面板」≠「我们也能」：未决请求属于**拥有它的那个进程**

- **日期**：2026-09-29（`CUSTOM-20260929-119`）
- **现象**：用户报"会话停在 AskUserQuestion，官方插件会弹出选项面板，我们的面板只有一个卡住的工具卡"。
  第一反应是"我们的渲染缺了"，于是先补了工具卡的 IN/OUT（117/118），**没解决**。
- **根因（两层）**：
  1. **能力声明缺失**：AskUserQuestion 在 ACP 里走 elicitation（form 模式），而 adapter 用
     `clientCapabilities.elicitation.form` 门控 —— 不声明时**连工具本身都被禁用**
     （`disallowedTools = ["AskUserQuestion"]`）。我们零 elicitation 支持 ⇒ 请求根本不会来。
  2. **进程归属**：即使补齐了声明，**别人进程里未决的请求我们也答不了**。实测
     （`CUSTOMIZATIONS/scripts/probe-elicitation.mjs --no-answer` 造出"卡住"的会话，再 `--reopen`）：
     `session/load` 只会**回放工具卡**，adapter **不会重抛提问**（elicitation 0 次）。
     官方插件能弹，是因为**它的进程一直持有那个未决请求**——面板只是没关。
- **解法**：声明 `elicitation.form` + 实现 `unstable_createElicitation` → 桥 → 面板表单（119）。
  于是**我们自己发起的会话**全程可用；**重开别人的会话**时不会弹（这是协议事实，不是我们的缺陷）。
- **教训**：
  1. **"另一边能做"要先问"它凭什么能做"**：官方插件与我们的差别不在渲染，而在
     **谁持有那个请求**、以及**有没有声明能力**。先去找"它有什么我们没有"，比先改 UI 快得多。
  2. **能力门控要读 agent 的源码**：`disallowedTools = elicitationSupport.form ? [] : ["AskUserQuestion"]`
     这一行直接解释了"工具压根没被调用"。协议里"客户端没声明 ⇒ agent 降级/禁用"是**常态**，
     遇到"agent 行为不对"先查自己声明了什么。
  3. **能力声明是行为开关，不是勾选框**：声明 form elicitation 的同一刻，MCP elicitation 与
     "拒绝回退确认"也会送进来——一个实现要同时吃下这三种，别只照着 AskUserQuestion 写。

## 33. 客户端模板字符串里的对象**没有类型检查** → 少一个必填字段，宿主静默丢弃

- **日期**：2026-09-29（`CUSTOM-20260929-120`）
- **现象**：工具卡的 `OUT` **永远空白**（用户报了三次）。同期 assistant 正文渲染正常，
  所以看起来像"工具正文的渲染器有问题"。117/118 两轮改了排版与渲染时机，**都没解决**。
- **根因**：`renderMarkdown` 的 item 形状在协议里是
  `{ entryId, sessionId, text, key? }`（`sessionId` **必填**），宿主的 `handleRenderMarkdown`
  对每个 item 跑 `verifySession(...)`，**拿不到 sessionId 就 `continue` 静默丢弃**。
  assistant 的 item 一直带着 sessionId，`toolCallView.pendingMarkdownItems()` 构造的**工具项漏了它**
  —— 于是工具正文的 markdown 请求到达宿主就被扔掉，卡上留一个空的 `.tool-text`，**两边都不报错**。
- **为什么工具链发现不了**：
  1. 客户端代码是**嵌在 TypeScript 模板字符串里的字符串**，`tsc` 不检查里面的对象字面量
     —— `sessionId` 是必填这件事只存在于 `protocol.ts` 的类型里，写漏了没人拦。
  2. `check-webview-client.mjs` 只做**语法**校验，能拦住反引号，拦不住"少一个字段"。
  3. **自查工具自己掩盖了它**：`preview-records.mjs` 的驱动脚本**替宿主回话**（直接
     `applyMarkdown(key, html)`），既没传 sessionId 也没做那一步校验 ⇒ 截图里 OUT 一直有内容。
     **测试替身/脚手架绕过的环节，就是 bug 藏身的地方**（pitfall #25 那条教训的第三次复发）。
- **解法**：`pendingMarkdownItems(sessionId)` 带上会话（调用方 `boot.requestMarkdown` 传入
  focused session）；同时把自查工具的驱动改成**也做那道校验**（缺 sessionId 就当作被丢弃并告警），
  这样它以后能拦住这一类。
- **教训**：
  1. **模板字符串里的对象要有"宿主校验"级别的守卫**：客户端脚本天然拿不到 tsc 的保护，
     凡是"协议必填字段"，要么让宿主在缺失时**报错而不是静默跳过**，要么在客户端测试里逐字断言形状。
     本次两条都做了（宿主那条断言在 `chat-panel.test.ts`，客户端那条在 `chat-client.test.ts`）。
  2. **"静默丢弃"是最贵的失败模式**：`if (!sessionId) continue;` 一行代码，代价是
     **三轮排查 + 用户三次复验**。这类守卫应当至少 `log()` 一次——写了日志，第一轮就能定位。
  3. **先假设"我改的那层没问题"是危险的**：前两轮都在改渲染（排版、时机），而问题在**请求根本没到**。
     定位它的正确顺序是：**先确认载荷到了没有**（抓包/探针），再谈渲染。

## 34. 同一事实有两份副本、而只有一份会被写 → 两份永不收敛，"没变化就不吭声"于是静默失效

- **现象**：切换模式时记录区出现**两条**提示，第二条把第一条又带了一遍：

  ```
  ⓘ Switched to Bypass permissions mode
  ⓘ Switched to Manual mode · Switched to Bypass permissions mode
  ```

  第二条描述的是一个**从未存在过的状态**——"Manual 模式 + Bypass permissions"是"新的一半 + 旧的一半"拼出来的。
- **根因**：`session.modes.currentModeId` 与 `configOptions[category='mode'].currentValue` 是**同一事实的两份副本**，
  而它们**不会同时被写**：
  - `SessionManager.setMode` 在会话有 configOptions 时**提前 return**（Claude Code 正是这种），
    那个唯一写 `modes.currentModeId` 的语句根本走不到；
  - `current_mode_update` 通知**从来不落到 SessionManager**（新面板下只有宿主自己的缓存收得到）。
  于是宿主的两条上报路径各看到一半：通知路径用 payload 拿到新 modeId、却留着**旧的** option；
  setter 路径读 SessionManager 拿到新 option、却读到**冻结的** currentModeId。
- **为什么静默**：整套设计靠一句话去重——「我们自己的 setter 与 agent 的通知谁先到谁提示，
  后到者 diff 为空」。这句话成立的前提是**两次报告的快照相等**，而它们**永不相等**。
  于是"没变化就不吭声"这条优化把一次切换报成了两次，而**没有任何检查会失败**：两条记录都是"正确"地产生的。
- **与 #19 的区别（这是它值得单独一条的理由）**：#19 讲的是**跨宿主 / 跨客户端**的重复，并断言
  「同一个文件里重复两份没关系（读代码时必然同时看到）」。这次两份副本**都在同一个进程、同一个类里**，
  字段名不同、类型不同，**grep 层面看不出来**——"读代码时必然同时看到"这个前提在这里并不成立。
- **与 #29 的关系**：#29 的教训是「凡是『以某一边的状态为真相』的优化（去重、跳过无变化的广播），
  都要问『另一边的状态能不能和它不同步』」。这次就是那个问题，而答案是**"能，永久地能"**。
- **解法**：让其中一份成为**权威**。这里选 config option（用户实际操作走的通道，也是 Claude Code 表达模式的那条）：
  快照的 modeId 由它派生；收到只带 modeId 的 payload 时把值**写回**那份副本；diff 跳过该选项（否则会被报两遍）。
  同时 `SessionManager.applyConfigOptions` 把值写回 `modes.currentModeId`，让其它消费者（`metaOf`、legacy 面板）也看到新值。
  代价写在明处：**测试里两条既有断言按新规则改写了**（"两通道表述一致"拆成"纯 modes 回退"与"有 option 时以它为准"；
  "mode payload 不丢选项"改成"其余选项不变 + mode 副本同步"）——改断言是因为**旧断言钉的是一个不可能出现的状态**。
- **教训**：
  1. **"两份副本"危险不危险，取决于"它们会不会同时被写"**，而不是取决于它们隔多远。
     同一个类里、字段名毫不相干的两份，照样可以永久漂移。
  2. **去重 / 幂等这类优化，它的前提要写进注释并当成契约来测**：这里的契约是"两条上报路径产出同一个快照"，
     而它从没被测过——测试把两个通道**分开**测（各测一次表述），从没测过"两条路径先后到达同一次切换"。
     补上的那条用例（`one switch reported through both channels is announced once`）是先红后绿的。
  3. **看到"顺序敏感的重复上报"时，先去看那个"后到者"凭什么认为自己没变化**——十有八九是它的基线
     和先到者的不是同一份。
- **来源**：CUSTOM-20260930-128（用户复验 123 时同时报的另一条）。

## 36. 空数组 ≡ "没有"？—— 它往往只是"这条路径还没填"

- **日期**：2026-09-30（做草稿页输入卡补全时，设计评审当场抓出来的两条）
- **现象**（代码还没写完就发现，所以没有用户可见的故障——但两条都必然发生）：
  设想一个"缓存某 agent 上一次会话的配置项/命令"的快照。它挂在会话事件上更新，
  分别在两条路径上被**空值覆盖**：
  - `loadSession` 的时序是「注册 placeholder（`configOptions: null`）→ emit `session-created`
    → 收到响应**才**把 `configOptions` 写进 placeholder」，**而且不走 `applyConfigOptions`** ⇒
    挂在 `session-created` 上的那次读取拿到的是空的，把上一次的好快照清掉。
    之后只有 `config_option_update` 通知能救回来，而实测的 replay 夹具里**一条都没有**。
  - `resumeSession` 的 `availableCommands` 恒为 `[]`（它不重放，所以那条通知永远不会来）⇒
    每 resume 一次，快照里的斜杠命令被擦一次。
- **为什么这类错误特别安静**：`[]` 与 `null` 在"这条路径还没填"和"这个东西确实没有"两种含义之间
  是**同一个值**。写代码时看到 `session.configOptions ?? []` 会本能地觉得"空就是没有，直接赋值即可"，
  而"这条路径晚一点才填"这个事实**只存在于另一个文件的行序里**（这里：`SessionManager.loadSession`
  的 emit 与赋值相隔 20 行）。
- **解法**（两条都要）：①补齐读取点——再挂一个**语义上更晚**的事件（这里是 `session-load-end`）；
  ②**空值不覆盖**：新值为空就保留旧值。代价是可能留着一份陈旧的列表，而陈旧是**无害**的
  （应用时逐项校验后跳过）；反过来"退化"会让功能自己消失。**陈旧 ≠ 退化**，这个取舍要写进注释。
- **与 #30 的关系**：#30 是"把『我手里没有这个信息』读成『这个东西不存在』"（面向对象侧），
  这条是它的**时序版本**——同一个误读，只是发生在"A 还没填"与"A 填了空"之间。
- **教训**：给"缓存 / 快照 / 派生状态"写更新时，逐个问一遍**谁在什么时候写它**；凡是存在
  "先 emit、后赋值"或"这条路径不填某个字段"的地方，就**不能**用 `?? []` 直接覆盖，
  也不能只挂那一个看起来最自然的事件。顺手写一条用例把时序钉住（本次两条各有专门用例）。
- **来源**：CUSTOM-20260930-151（设计评审阶段）。

## 37. 把「协议层的轮次结束」当成「agent 干完了」→ 后台任务还在跑，界面已经恢复成空闲

- **现象**（用户报）：任务还在跑（在等子 agent），聊天面板的发送按钮却已经变回普通状态，
  消息还停在半句话上。
- **根因**：`running` 的判据是**"该会话的 `session/prompt` 请求还没返回"**——一个**代理信号**
  （#25/#26 的老毛病：用代码层面的东西去近似"用户看到的事实"）。ACP 的"轮次"与"agent 还有活没干完"
  是两件事：Claude Code 的后台子任务（Task 工具带 `run_in_background`）**在轮次结束后继续干活**，
  它的产出之后以轮次外的 `session/update` 通知到达（还带 `_meta."_claude/origin".kind =
  "task-notification"` 这个私有标记），完结时以 `<task-notification>` 注入块回到会话里。
- **解法**：把"运行中"改成**两台信号或起来**（`isTurnInFlight || backgroundTasks.has`），
  后台任务单独一台状态机：**进入要有证据**（tool call 的 `rawInput.run_in_background`）、
  **产出型通知续期**（housekeeping 通知不算，否则空闲会话也会被钉上 Stop）、
  **退出三条**（任务汇报 / 新轮次 / 静默超时），其中超时那条**必须发通知**——
  静默地恢复正是用户报的那种观感。
- **教训**：判据要问"**用户看到的事实是什么**"，而不是"我手上恰好有什么信号"。
  代理信号能撑住一段时间，是因为大部分情况下两者碰巧重合；一旦有"轮次之外的工作"这种形态，
  它就会以"界面比事实更早乐观"的方式暴露出来。**别急着补一个更宽的阈值**（那种"最近 N 秒有动静
  就算在跑"的写法覆盖不了长静默），先找**有没有直接信号**——这里有（后台任务的启动入参与
  汇报注入块），只是它们不在"轮次"这个概念里。
- **来源**：CUSTOM-20261001-162（用户报 + 日志取证）。判据不生效时看落盘日志里有没有
  `keeps running outside the turn (a background task was launched)`——它没出现就说明
  该版本 adapter 没带那个入参，而不是状态机坏了。

## 38. 模块级布尔 = 全局状态：凡「属于某个东西」的状态，先问它属于谁

- **现象**（用户在同一天报了两次，形状一样）：①置顶条的"收起"按一下，**切到别的会话 tab 再切回来就弹回展开**；
  ②表单抽屉在某张表单上被收起过，**下一张表单**一冒出来就是收起的（用户从没对它按下过那个按钮）。

- **根因**：两处都是 `var collapsed = false` —— 一个**模块级布尔**。UI 上它读作"这一条置顶卡 / 这一张表单怎么显示",
  而它实际的作用域是"这个 webview 文档"。于是既会**串**（A 的折叠影响 B），又会**丢**（切回来时没人替它恢复）。

- **解法**：把它挂到它真正的主语上 —— 置顶条按 `sessionId`（`collapsedBySession`，会话 id 由 boot 在焦点咽喉点同步进来），
  表单按 `promptId`（`dismissed` 本来就按 promptId 记，`collapsed` 只是那张表单的视觉态，换一张就复位）。

- **教训**：写一个 `var xxx = false` 之前问一句"**它是谁的**"。答案不是"这个文件"的时候，它就必须按那个东西存。
  这也是本仓库反复出现的同一条：**状态没有归属，就会以"有时串、有时丢"的方式表现**（#19 的两份副本、#34 的两份事实、
  165/§5.38 的"按会话状态"清单，都是它的不同侧面）。顺手加一条判据：**用户说"每个 X 自己保持"时，代码里就该出现 `byX`**。

- **来源**：CUSTOM-20261001-166（用户报 + 同轮扫出的表单抽屉同类问题）。

- **复发记录（2026-10-04，`CUSTOM-20261004-188`）**：同一个文件里**同一个错误的下一个字段** ——
  表单抽屉的**当前页**也是模块级的一个数字（`var activeTab = 0`）。166 修了 `collapsed`，`activeTab`
  原样留着。现象：用户报"弹出选项面板，有时候会默认聚焦到最后一个选项 tab"。
  机制更阴一点 —— 它不是简单的"串"，而是**串 + 161 的夹回**两件事相乘：161 为了让"题数变少的表单"
  不指向不存在的页，写了 `if (activeTab >= groups.length) activeTab = groups.length - 1`，
  而这个夹回是相对**当前表单**的题数做的，变量却是全局的 ⇒ 上一张停在第 4 题（`activeTab=3`）、
  新的一张只有 2 题，夹回把新表单**主动**放到最后一页。**所以"有时候"= 新表单比旧表单短的时候。**
  修法：`activeTabs[promptId]`（缺省 0 ⇒ 新表单天然从第一页开始）。
  **教训升级**：①扫"模块级状态"时不要只修**用户报的那个字段** —— 同一个作用域里往往还躺着它的兄弟
  （166 修 `collapsed` 时 `activeTab` 就在同几行里，隔 480 行被用到）。②**"夹回/纠正"这类守卫会把
  "串"从显性变成隐性**：没有夹回时越权只会显示一个空页面（一眼可见），有了夹回就变成"看起来正常、
  其实错了"（本次就是）。凡是给跨作用域的值加兜底夹回，先问它夹的是谁的范围。

## 39. 「点了没反应」先问：他点的是哪一个？—— 我修好了没人点的那个按钮

- **现象**：用户报"悬浮框里的收缩按钮点了还是触发的定位，收缩没生效"。我上一轮刚把那个按钮从 15×16px
  放大成 16×20 + 常驻淡底，还用无头探针（`elementFromPoint`）证明它**没有被遮挡、点击确实生效**。

- **两件事同时成立，所以诊断看似完备**：左侧通道里那个小方块（我加的）**确实能用**；而用户点的其实是
  **卡片里的折叠三角**（`.fold-caret`）—— 他说的"悬浮框**里**的收缩按钮"是字面意思。那个三角上叠了
  两套机制：原生的 `<details>` 开关 + 冒泡到 host 的"点击跳转"，于是"点一下既折叠又跳走"，折叠立刻
  被跳转抹掉。

- **教训**：①**"我修的那个控件" ≠ "他点的那个控件"**。用户描述里带方位词（"里"、"左边"、"上面"）时，
  先按字面去找那个元素，而不是找功能最接近的那个。②**同一元素上叠两套机制**（原生行为 + JS 行为）是
  隐形冲突：两边各自"都生效"，合起来互相抵消 —— 表现成"都没生效"。堵的时候要把两边的入口都堵
  （`preventDefault` 管原生、`stopPropagation` 管冒泡）。
- **来源**：CUSTOM-20261001-166→167（用户第二轮复验）。

## 40. 用"下一条**已渲染**的位置"做上夹 → 被顶出去的那张永远残留一条边

- **现象**：把置顶卡从"只钉一条"改成"整段前缀"（172）时，每张卡共用一套落位公式，只差"这一轮的
  结束位置"取哪个量。我一度取**下一条卡已经渲染出来的位置**（`T_{i+1} - 卡高`）—— 看上去更整齐：
  两张卡永远严丝合缝。但在"新卡已钉在判定线上"的那一帧，新卡 `T = TOP_GAP` ⇒ 旧卡被夹在
  `TOP_GAP - 卡高`，底边正好停在判定线上 ⇒ **旧卡永远剩最后 3px 露在外面**，"直到卡片 A 看不到"
  永远不会发生（用户第 4 步要的正是这件事）。

- **为什么难发现**：三条提问以上时它**是对的**（更靠前的卡被更靠前的结束位置一路夹成负值、被裁掉），
  所以一屏多条提问的截图里一切正常；只有"两条提问、且第二条刚好钉住"这一个姿态才露馅 ——
  而那正是读者每天盯着的那一帧。

- **正解**：上夹锚**布局量**（下一条用户消息的 `offsetTop - scrollTop`，随滚动线性减小），不锚
  下一条的渲染位置。旧卡于是会一路滑到负值、被 `overflow: hidden` 裁掉；反向滚动又原路抽回
  （公式逐条独立、方向无关）。

- **教训**：①**"用渲染结果算布局"会把一个量变成两条互相依赖的链**，其中一条会自我锁定（钉住的那张
  不动 ⇒ 它上面的那张也不动）。只有布局量（自然位置）是单调、无反馈的。②改了这类公式，除了量
  "正常那一帧"，**必须量边界那一帧**（这里是：只剩两条、且最新那条刚好越线）。
- **来源**：CUSTOM-20261002-172（用户复验 171 后报"永远只钉一条 / 上滑不会抽回"）。

## 41. 测试桩的 `insertBefore` 没建模"移动" → 重排子节点的代码静默乱序

- **现象**：卡堆重排（把 host 的子节点对齐到"该渲染的那几张"）在真浏览器里逐帧正确，桩 DOM 里却
  稳定地留下**错的那一张**：该顶出去的那张还在、该钉住的那张没了，`marginTop` 还是上一帧的值。

- **根因**：桩的 `insertBefore` 只做 `splice(at, 0, child)`，**没有先把 child 从原位置摘掉**；真 DOM 的
  `insertBefore` 是**移动**（已在树里的节点先摘再插）。于是桩里出现了同一个对象的**两份引用**，
  客户端随后"删掉多余的"（`while (childNodes.length > n) removeChild(lastChild)`）时，`removeChild`
  按 `indexOf` 找到的是**第一份** ⇒ 删掉了另一张卡。

- **教训**：①测试替身要**按被调用 API 的契约**建模，不是"够用就行"——"移动"就是 `insertBefore` 语义的
  一半；漏掉它，任何重排已有子节点的代码都会在桩里拿到假结果，而症状（顺序错乱）看起来完全像业务 bug。
  ②**两边都修**：桩补上移动语义，客户端也不再依赖它（显式先摘再插）—— 依赖一个"只有真 DOM 才保证"的
  语义，本身就是那条属性没被测试覆盖的证据。
- **来源**：CUSTOM-20261002-172。

## 42. 诊断通道自己有配额，而噪声先到 → "日志里没有"被读成"没执行"

**现象**：排查「表单的选项说明丢了」时，上一轮特意加了一行真机诊断（`[acpc] form fields: N question(s), M option(s), K with description`，
CUSTOM-20261002-168），计划"真机再看时日志会直接给出答案"。真机跑完之后去查日志：**一行都没有**。
于是很自然地得出"这段代码没跑到 / 这个窗口是旧构建"的结论 —— 而这两个结论当时都**没有别的证据**，排查就此卡住。

**根因**：客户端日志桥（`html/client/boot.ts` 的 `installLogBridge`）当时是「**每次加载共 50 条**」的**终身**上限。
那 50 条被 `[acpc] renderMarkdown asked` 抢在**前面**用掉了：真机日志显示 50 条全部产生于
`04:10:02.551`–`04:10:02.744` 这 **193 毫秒**内（一次会话加载把整段记录重渲染，每渲染一批就报一次）。
配额用尽之后，`forward()` 对后续一切 `console.warn` 直接 `return` —— **诊断不是没执行，是没资格进日志**。

**为什么特别坑**：配额耗尽的时机**恰好是最先出现的那类消息**，而它们（markdown 渲染进度）恰恰是最不重要的；
真正需要的诊断总是来得晚。再加上上限是"终身"而不是"滚动"，一个开了一整天的 webview 从上午就已彻底静音。

**解法（CUSTOM-20261002-173）**：
1. 配额从"终身 50"改成**滚动窗口**（10 秒 30 条）——窗口一滑就恢复，长命 webview 不再被永久静音；
2. 给最大的噪声源本身限流（那条 markdown 诊断只报前 3 次 + 每 25 次一次）；
3. 更根本的一条：**加构建指纹**（宿主 activate 一行 + `<body data-acpc-build>` + 客户端 boot 第一条日志），
   让"这个窗口跑的是哪份代码"变成**直接可读的事实**，不必再靠"没重启过 + 代码是新的"这种间接推理。
   这三处的说明见 `docs/arch/chat-panel.md` §5.39。

**教训**：**"我在日志里没看到它" ≠ "它没发生"** —— 只有当你能证明这条通道当时还有配额时，缺席才是证据。
凡是给排查用的证据通道，都要先问一句：*谁会先说话？配额够吗？* 另外，"临时诊断"加上去之前，
先确认它落到的那条路不会先被别人堵死（本次的 markdown 诊断就是堵路的那个人，而且它自己当初也是"临时诊断"）。

## 43. 把"两端各证一遍"当成"整条链通了" —— 真正丢数据的那一跳没人走过

**现象**：用户报「表单的选项说明（description）不显示」，报了三轮。每一轮我都能"证明客户端是好的"：
真实报文里有 `description`（贴过日志原文）、`fieldsOf` 解析后 4/4 都在（跑过脚本）、无头预览也能把说明渲染出来
（截过图）。可用户面板里就是没有。第三轮靠 173 加的构建指纹当场排除"旧窗口"，诊断才吐出关键的一行：
`[acpc] form fields: 1 question(s), 4 option(s), **0 with description**` —— **数据到客户端时就已经没有说明了**。

**根因**：ACP SDK 用 zod 校验入站请求（`@agentclientprotocol/sdk/dist/acp.js` 里
`validate.zCreateElicitationRequest.parse(params)`），而 0.21.1 的选项 schema 是
`zEnumOption = z.object({ const, title })` —— **没有 `description`（也没有 `_meta`）**。
zod 的 object 默认**丢弃未声明的键**，于是 adapter 明明发了说明，在**进入我们代码之前**就被削掉了。
**实证**：把真机报文先过一遍 `zCreateElicitationRequest.parse`，`4/4 带说明` → `0/4`。

**为什么前三轮的验证全都是假绿**：三次都拿**日志里的原始报文**去喂 `fieldsOf` —— 而日志记的是
**JSON-RPC 原始流量**，当然带着说明。也就是说我验证的是「A 端有、B 端能处理」，**中间那一跳（SDK 解析）
从来没人走过**。两端都对，链照样断。

**解法**：**已根治**（CUSTOM-20261003-175）—— `@agentclientprotocol/sdk` 升到 1.7.0（1.3.0 起
`zEnumOption` 补上了 `description`/`_meta`），真机探针验证说明确实回到了我们这侧。备选的短期绕行
（从同一 `toolCallId` 的 AskUserQuestion 工具调用 `rawInput` 补回 —— 那一层在 zod 里是 `z.unknown()`、
没被削）**没有采用**，不再需要。

**教训**：**"输入有 + 输出端能处理" ≠ "链路通"**。要证明一条链，必须从**真实入口**灌一次数据，
让它走完**每一跳**（这里的一跳是别人的库，正是最容易漏的那一跳）。
具体到本项目的排查套路：能跑通"真机报文 → 真实调用链 → 断言"的就不要拿两段各自证明；
桩/脚本**替换掉的每一层，都是一个没被验证的洞**（与 #19「同一份知识存两份」是同源问题）。

## 44. 边读边写 → O(n) 次强制重排（"布局抖动"的教科书形态，就藏在最热的那个循环里）

- **日期**：2026-10-04（`CUSTOM-20261004-180`）
- **现象**：用户报「消息面板内容很长时，点击卡片进行收缩/展开都会导致界面长时间卡顿」——几千条记录的会话里点一下要僵好几秒。
- **根因**：`rail.measure()` 在**同一个循环里**边读边写 —— 读一次 `getBoundingClientRect()`（节点首行中心）、紧接着写一次 `dot.style.top`。浏览器的规则是：**任何样式写都会让后续的布局读强制重排**。于是 n 个标记 = n 次强制布局；再叠上每次重排都要走完整棵子树，就是那几秒。
- **为什么一直没发现**：这段代码是"每帧只量一次、稳态不量"的优化过的热路径，读起来完全合理（缓存在 `points[]`、`rebuild` 有签名去重）；而且**功能完全正确** —— 只是慢。用户不报就不会有人去数强制重排。
- **修法**：**两段式** —— ① 只读（容器几何 + 每个节点的一行中心，全部收集进数组）② 只写（hidden / top / 引导线）。输出逐字不变（`points` / 圆点 `top` / 线），但强制重排从 n 次降到 1 次。
- **怎么钉住它**（毫秒在无头预览里不可信，见下）：桩单测里把"几何读取"与"样式写入"都记进一条**时间线**，数 `写→读` 的来回次数 —— 旧版 O(标记数)，新版常数级（24 个标记实测 ≤4，那几下是收尾的 `applyScroll`/`syncActive`）。
- **教训**：**热路径上"读一批、写一批"是一条纪律，不是风格偏好**。凡是循环里既有 `getBoundingClientRect`/`offset*`/`client*` 又有 `style.*`/`classList`/`hidden` 的，默认就该怀疑它。量它的正确姿势是数**强制重排次数**或钉**读写时间线**，而不是量耗时（无头预览跑在 `--virtual-time-budget` 下，`performance.now()` 是虚拟时钟 —— 第一版量出 3010ms，纯属虚拟时间在跳）。

## 46. 同一个输入在两种状态下做相反的事（回车 = 发送 / 停止）

- **日期**：2026-10-04（`CUSTOM-20261004-182`）
- **现象**：用户报「输入框消息发出之后，再按一次 Enter 会触发停止」——发完消息手还在键盘上，第二条回车把**整轮**停掉了。
- **根因**：回车与 Send/Stop 按钮共用一条路由（`state.running ? cancel() : send()`）。按钮那样是合理的：它的 `title`/`aria` 会翻成 `Stop`，用户**看得见**自己在按什么。回车没有这个提示，而它的默认预期是"发消息"。
- **为什么特别糟**：这两个动作的**量级完全不同** —— 发送可重来（草稿还在），中止整轮不可逆（工具调用被掐断、agent 正在做的事丢了）。把不可逆的那个挂在"最顺手的那根手指"上，误触成本由用户承担。
- **修法**：回车只调 `send()`（它自己守着"跑着不发、空内容不发"，于是跑着按回车 = 安全空操作）；停止保持显式（按钮 / Escape）。
- **教训**：**一个输入不该在两种状态下做相反的事，除非当下就有可见的提示**。拿不准时，让"危险的那个"多一步（按钮、菜单、确认），让"顺手的那根手指"只做可逆的事。

**同一天的第二步（`CUSTOM-20261004-183`）**：用户接着要求「Escape 不管触发停止还是关弹窗，都是不可逆的，
需要先弹二次确认框」。先把事实核了一遍 —— 只有**停止**不可逆（工具调用被掐断）；关菜单/浮层都能重开，
表单抽屉的 Escape 只收起且打过的字全在 ⇒ 只给停止加确认（其余保持一键，多一步只是添堵）。
做法是在输入卡上方加一条 `#stopConfirm`（不抢焦点、不模态），Escape 与 Stop 按钮都先经过它。
**顺带一个布局坑**：它必须放在 `.composer-inner` 里 —— `.composer-main` 是 flex **行**，
挂在它下面会被压成 **0 高**（读数 `stopConfirmH: 0`，而截图里"什么都看不到"和"没渲染"长得一模一样）。

## 47. 同一类资源有两条渲染路径，而只有一条接上了"点击通道"

- **日期**：2026-10-04（`CUSTOM-20261004-184`）
- **现象**：用户发来一张截图 —— 助手回复的表格里，agent 给的 `GOAL.md:74` / `AGENTS.md:596` 这类文档跳转
  链接**看着能点，点了没反应**（鼠标悬停浮出 `Blocked link scheme`）。
- **根因**：本地文件**早就有**一条完整通道：`contentBlocks.localPathOf` 判出本地路径 → chip 写 `data-path`
  → `links.ts` 委托 → `openFile`（按会话 cwd 解析相对路径 + 跳行号）。它是为**内容块 chip**（`resource_link`）
  建的。而 markdown 正文里的链接走的是**另一个函数** —— `markdown.ts` 的 `link()`，那里的判定是
  「`http`/`https`/`mailto` 放行，其余一律降级成 `link-blocked` 静态 span」。于是**同一个本地文件**，
  以 chip 形式出现能点开，以 markdown 链接形式出现就是个死字。
- **为什么藏得住**：两条路径都"工作正常"，各自的代码读起来都合理；没有任何自动检查会问
  「这两条路径对同一类资源的判定一致吗」。而 `link-blocked` 的样式（灰 + 删除线 + `cursor: help`）
  在截图里和普通文字**几乎分不出来** —— 用户看到的是"链接"，我看到的是"已经按设计处理过的链接"。
- **修法**：把 `localPathOf` 导出，`link()` 在 scheme 判定失败后调**同一个**函数；命中就写 `data-path`
  （顺带支持 `:12` / `#L12` 行号后缀）。**剥行号必须早于路径判定** —— `GOAL.md:74` 里 `GOAL.md` 本身
  就是合法 URI scheme 语法（`.` 是 scheme 允许字符），不剥会被判成"scheme 为 goal.md 的外链"。
- **教训**：①**"这类东西能不能点"是一个判定，不是两个**。凡是"资源 → 该走哪条通道"的知识，
  全仓库只该有一份（同 #19）。②`Blocked …` 这类**安全兜底分支**天生有"伪装成正常处理"的倾向：
  它不报错、不抛异常、也不进日志，样式还常常**故意做得低调**。给它加任何"看着像能点的东西"之前，
  先问：*这条兜底会不会吞掉一类本来有通道可走的输入？* ③跑一遍真实渲染（`node -e` 喂几个 agent 实际会写的
  形状）比读代码快得多 —— 这次的 `#L12`、`C:/x:12`、`<a"b>` 转义三件事都是**量出来**的，不是想出来的（同 #31）。

## 48. 协议里两个字段"看着都对"，量纲却不同 —— 我们挑错了那个

- **日期**：2026-10-04（`CUSTOM-20261004-185`）
- **现象**：用户报"上下文进度会出现超过上限的情况"，截图里圆环满格、tooltip 写着
  `100% · 1841k / 1000k tokens`（窗口是 1M，却显示用了 1.84M）。
- **根因**：宿主把 **`PromptResponse.usage.totalTokens`** 折进了圆环的 `used`，而圆环要的是
  **"当前上下文占用"**。ACP 协议里这两个是不同量纲的字段：
  - `UsageUpdate.used` = *Tokens currently in context*（≤ size）
  - `Usage.totalTokens` = *Sum of all token types **across session*** —— 实测 `claude-agent-acp`
    的实现就是每轮 `accumulatedUsage.inputTokens += …`，**且 cache read 每轮都重算**，
    所以它只增不减。长会话必然越过窗口上限。
  写入时 `size` 沿用旧值，于是"1.84M / 1M"这种荒谬读数被渲染出来；而圆环本身 `clamp(0,1)`
  ⇒ **环满格、数字超限，两者自相矛盾**。
- **为什么一直没被发现**：那个分支当初的理由是"没发 `usage_update` 的 agent 也能有读数"，
  听起来是纯增益。实际上它**不可能生效**：没有 `usage_update` 就没有 `size`，客户端在
  `!size` 时直接隐藏表盘 —— 于是它唯一存在过的作用就是**把已经正确的读数改坏**。
- **修法**：删掉那个写入者，表盘只认 `usage_update`（要展示"会话累计 token / 花费"就**另开字段**，
  别复用 `used`）。顺带把 tooltip 里的金额 `toFixed(2)` —— agent 给的是一枚裸浮点
  （日志实测 `2.6394680000000004`），原样拼出去就是"4.676045 USD"。
- **教训**：①**同一个名字（`usage`）不代表同一个量**。读协议字段时看的是**它的定义**，不是它像什么；
  两个来源往同一格写之前，先问"这两个数的**单位和语义**是不是同一个"。②"看起来是纯增益的兜底"
  要能说清**它在什么条件下真的生效** —— 说不出来就说明它只在破坏数据（同 #30：把"我手里没有这个信息"
  读成"这个东西不存在"）。③**把外部 Agent 的源码读一遍**是能最快定案的证据：一条
  `accumulatedUsage.inputTokens +=` 就把"到底谁在累计"钉死了，比在自家代码里猜快得多。

## 49. 异步回填 + 会增长的数据 = 冻在"请求发出那一刻"的那一版

- **日期**：2026-10-04（`CUSTOM-20261004-186`）
- **现象**：用户报"有时候消息显示不全"，截图里一条很长的助手回复**只显示开头 8 个字**
  （`后端**没事`，`**` 还是字面量），后面什么都没有；同一条消息在 agent 自己的会话记录里是完整的。
- **根因（三件事叠在一起）**：
  1. **请求带的是一份快照**：`renderMarkdown` 的 item 里是 `{entryId, text}`，宿主按那段 text 渲染。
     而适配器 `includePartialMessages: true` ⇒ 一条消息拆成**很多** `agent_message_chunk`，
     宿主每来一片就整条 entry 重发一次 ⇒ 客户端手里的文本一直在长。
  2. **128 让记录"一落地就自己发起渲染请求"**（初衷是治"一轮最后一条记录永远拿不到渲染"），
     于是**第一片**到达时就问了 —— 回填回来的是**那一片**的渲染结果。
  3. **作废信号传不过去**：宿主 store 合并时确实会 `last.html = undefined`，但 `JSON.stringify`
     **丢掉 undefined 键** ⇒ 客户端那份 `entry.html` 永远不被清理，`applyAssistant` 见 `hasHtml`
     就把正文重设成那份**旧渲染**。于是正文冻在第一段上，而且两端都没报错。
  （工具卡那条路 `084` 早踩过同一个坑，用"key 里带文本指纹"治好了；助手/思考这条一直没治。）
- **为什么"有时候"**：只有在**回填比后续分片先到**时才冻住 —— 也就是"这条记录后续还会流一会儿"
  的情况。恰好收尾的那一刻才回填的短消息永远正常。用户在**长回复**上看到，正是这个形状。
- **修法（两边都判"只认领自己渲染的那段文本"）**：
  - 宿主 `handleRenderMarkdown`：`item.text` 与 store 里当前 `entry.text` 不符 ⇒ **不落盘、不回填**
    （否则下一次快照——切会话/重开——会把"只渲染了开头"的版本当成当前内容发出去）。
  - 客户端 `patch`：记 `asked[entryId]`（这次问的是哪段文本），不符的回填**丢掉**；且
    **文本变了而这一 patch 没带新 html ⇒ 手里的 html 作废**（补上宿主那条过不来的规则）。
    收尾时的自愈路径同时收紧：只要"没有可用的新 html 且记录已收尾"，就把**当前**文本重新要一次。
- **教训**：①**任何"请求 → 异步回填"的通道，都要能回答"这份回填对应的是哪一版输入"**。
  只带 id 的通道在输入**不变**时才成立；输入会增长（流式文本、工具输出）就必须带指纹或回比。
  ②**`undefined` 不是一种能过线的值**：用"把字段置回 undefined"表达作废，跨 `postMessage` 就消失了 ——
  作废必须用**存在**的信号表达（显式标志位，或如本例的"文本对不上"）。③"有时候"三个字指向的是
  **时序**，不是概率：把"两条路径谁先到"写下来，"有时候"就会变成一条确定的序列（这条也是 #43 的同族）。

## 50. `appendChild` 到**同一个父级**也会失焦 —— 别在每次输入时"顺手搬一下"

- **日期**：2026-10-04（`CUSTOM-20261004-189`）
- **现象**：用户报「选项的弹出面板，在附加内容输入框输入内容时（以及 Other 里的自定义输入框），
  **每输入一个字符就会失去焦点**」—— 打字只能打出第一个字。
- **根因**：`placeCustomBoxes`（表单抽屉里"把题目级的自拟框移进被选中的那一行"）每次 refresh 都
  无条件 `host.appendChild(box)`，而 refresh 由 `onDrawerChange` 在**每个 `input` 事件**上触发 ⇒
  每敲一个键就把那个框搬一次。`appendChild` 的 DOM 语义是**先摘下来再插回去**，而"摘下来"会触发
  浏览器的失焦步骤（焦点回到 `body`）——**即使插回去的还是同一个父级**。
- **为什么值得记一笔**：这条看起来像"常识"（搬动会失焦），但**两个方向都容易想错**：
  ①以为"同一个父级不算搬动"（错，实测照样失焦）；②以为"值不会丢所以随便搬"（值确实不丢 ——
  代码注释当时就是这么写的："appendChild MOVES the element: its typed value survives"，
  漏掉的正是**焦点**这一项状态）。按 #31 的规矩这条只能量：`preview-records.mjs` 新增
  `#elicfocusprobe` —— 真 Chromium 里把已聚焦节点的祖先 `appendChild` 到**同一个**父级，
  读 `document.activeElement`，得到 `focusAfterSameParentMove: false`。修完同一个探针读到
  `focusedAfter: true`（连打三个字符焦点都在）。
- **修法**：`if (box.parentNode !== host) { host.appendChild(box); }`（回"老家"那条同理）。
  判据从"搬到哪儿"变成"**要不要搬**"。
- **教训**：①**每次输入都会跑的那条路径（refresh / re-render）里，任何 DOM 搬运都要先问"它已经
  在目标位置了吗"**。这类路径的代价不止失焦：滚动位置、文本选择、`:focus-within`、正在播放的
  transition 都会被打断。②"把值不丢"当成"搬得没问题"是**只盯了一个状态**（本仓库 #19/#34 的
  同族：一个事实有多份状态时，只保住一份就等于没保住）。③**"同一父级"不是安全区** ——
  判断要不要动 DOM，看的是"位置是否已经正确"，不是"位置是否变化"。

## 51. 动画元素被重建 = 动画永远停在第一帧（以及量动画的三个陷阱）

- **日期**：2026-10-04（`CUSTOM-20261004-190`）
- **现象**：用户报「任务进行中时，上下文圆环外围的闪烁效果失效了（现在只能看到下面多了一段圆环）」。
- **根因**：外圈那条 CSS 动画（`animation: gauge-spin 1.5s linear infinite`）挂在 `<svg>` 的子节点上，
  而 `renderContext` **每次都重建整个表盘**。重建 = 新节点 = 动画从 0 开始。而 `setRunning` 会走到
  这里，它又由 `sessionsChanged` 驱动，宿主**每收到一个 `agent_message_chunk` 就 `refreshSessions()`**
  ⇒ 流式期间每秒重建几十次 ⇒ 那条弧永远停在起点角度：**看起来就是"多了一段不动的圆环"**。
  （CSS 一个字都没错，`animationName` 量出来就是 `gauge-spin` —— 错的是"谁在不停把它拆了重装"。）
- **修法**：`renderContext` 记住上次画的是哪组数字（`used/size`），**数字没变就只改 class/title，不碰 DOM**。
  于是 `setRunning` 退化成"翻一个类名"，动画活下来。
- **量动画的三个陷阱（这次全踩了一遍，别重复）**：
  1. **无头浏览器 `prefers-reduced-motion` 恒为 `reduce`**（实测 Edge headless），而本仓有一条全局
     `* { animation: none !important }` 兜它 ⇒ 在无头里**永远量不到动画在跑**。用 `!important` 压的
     东西**inline style 也压不动**（我试过，`animationName` 还是 `none`）。
  2. **元素不在渲染树里就没有 Animation 对象**：`#gauge` 档的 composer 是 `display:none`（183 记过
     这条既有现象），于是 `getAnimations()` 空、`getBoundingClientRect()` 是 `0x0` —— 读数像"动画坏了"，
     其实是这一档根本看不见它。要量得借一个 composer 可见的相位（`#ready…`）。
  3. **`--virtual-time-budget` 下动画的 `currentTime` 不推进**：连打两次采样都是 0，也会被读成"没动"。
  **所以判据不该是动画时钟，而是它的成因**：调一次 `setRunning` 之后那颗 `svg` 还是不是**同一个节点**
  （`#gauge-rebuild` 档，`sameSvgNode` / `secondCallKept`）。节点身份是确定的，动画时钟不是。
- **教训**：①**给"会动的东西"做重绘前，先问它是不是靠"同一个节点一直活着"才有动效** —— 动画、过渡、
  正在播放的媒体、CSS 计数器都算。②一条链上"每个事件都重算"的路径（这里是 chunk → refreshSessions →
  setRunning → renderContext），其代价往往不在它自己那一行，而在**它下游某个"重建"**。③**量不到就
  换个判据**，不要把一个假阴性读成"功能正常/坏掉"（#25/#26 同族）。④**harness 读的是 `out/` 编译产物** ——
  改完源码不 `npm run compile-tests` 就量，量到的是**上一次的代码**（这次差点把修好的当没修）。


## 52. 「落点」按元素定义 + 提示线不清除 ⇒ 看着有落点、松手却什么都没发生

- **日期**：2026-10-08（`CUSTOM-20261008-201`）
- **现象**：用户报「tab 拖拽现在能拖动了，但松开左键后就复位了（没有插到预期的位置）」。而现场看到的
  指示线**就在预期的位置上** —— 一个"明明有落点"的画面。
- **根因**：两件事叠在一起，各自都不显眼：
  1. **落点只长在元素上**。198 把 `dragover`/`drop` 挂在每个 `.tab` 自己身上，而 `.tabs` 是
     `flex: 0 0 auto` ⇒ **最后一个 tab 右边的空白属于 `.tab-strip`**、tab 之间的 `gap: 2px` 也不属于
     任何 tab。指针一旦落在这些地方，浏览器就没有可接受的 drop 目标 —— 松手即复位。
     **两种最自然的拖法（拖到最后、拖到两个之间）正好都落在这里。**
  2. **提示线不会消失**。线是 `dragover` 时画上的，而**没有任何 dragleave 去清它**：指针从 tab 挪到
     缝里那一刻起，画面上"有落点"、实际上"已无落点"—— 用户据此以为松手会生效。失败于是完全静默：
     没有任何异常、没有任何日志、界面只是"没反应"。
  3. `dragend` 清的是整套拖动状态，所以松手后连线的残留通常也看不出来 —— 更像"点了没反应"。
- **修法**：落点容器换成**整条 `#tabStrip`**，插入位由**指针横坐标与各 tab 中点**算出来（`boundaryFor`
  → 0..n），指示线由**同一个数字**决定（`markBoundary`）；`dragleave` 只清线、不清拖动。
  另加两条常驻诊断（`tabdrag start=` / `drop from=… to=…`），把 DnD 这条静默链路变成可读的。
- **教训**：
  ① **"落点"要按容器定义，不能按元素定义**。凡是 flex 行（tab 栏、工具条、列表）都有**缝**与**末尾空白**，
     它们属于父容器 —— 拖拽/放置类交互的命中外沿必须画在容器上，位置用坐标算（本仓同族：pitfalls #24
     "别用常量去对齐，锚到已经在正确位置上的元素"）。
  ② **提示与实际行为必须同源**。指示线是"会发生什么"的预告，它只能由**落点计算**那一个数字画出来；
     任何"上一次命中了谁"式的旁路（198 是从 dragover 的目标直接推侧别）都会在边界处说谎。
  ③ **静默失败要留诊断**。DnD 的失败在界面上就是"没反应"，肉眼与截图都判不出来 ⇒ 两条能区分
     "start 没跑 / drop 没到 / 落了但顺序被覆盖"的日志，比再猜三轮都值（#35 的同族）。

## 53. 「点了没反应」有一半是主线程长任务 —— 输入被压后/丢掉，症状却像"处理器没接上"

- **日期**：2026-10-08（`CUSTOM-20261008-202`）
- **现象**：用户报「在 New Session 打开历史会话时，loading 的过程中没法切换到其他会话 tab」。
  界面上是"点了完全没反应"：tab 不切、也没有任何报错，而同一时刻**面板自己还在正常渲染记录**。
- **根因**：一批 markdown 回填（139 条）在**一个任务**里跑完：每条都要消毒、插 DOM，并且读一次几何
  （`patch` 收尾的 `follow()` 读 `scrollHeight`）。那是一条 581 条记录、2428 个工具卡、17000px 高的
  转录 ⇒ 几百次"写一段、读一次几何"交错 = 几百次**强制整页重排**，合成一个几十秒的长任务。
  **长任务期间浏览器把输入事件压后甚至丢掉**，于是"点了没反应"和"处理器没接上/状态没同步"长得一模一样。
- **怎么认出来的（这套判据值得照抄）**：真机日志里客户端**连续 50 秒一行都没有**（同一时间宿主也一行
  没有，但 `session/load` 的响应早就到了 ⇒ 卡的是客户端），而恢复后的第一刻打出来的正是那次
  `press@outside` —— **被压后的点击**；紧接着是攒了一路的 4 条 `markdownRendered` 一次性涌出。
  "日志突然断了 + 恢复后一次性涌出 + 用户的手势出现在恢复的第一刻"这三条凑齐，就是输入饥饿。
- **修法**：① 那条只为诊断读的几何，改成"只在它真会被记下来时才读"（诊断自己也有节流/配额，本来
  大多数调用都不会记 —— 读它是纯浪费）；② 回填应用**按时间片**（每片 ≤8ms）落地，单任务不超过一帧；
  ③ 加一个常驻的 `longtask` 看门狗（>300ms 记一行，带"当时在做哪一段"）。
- **教训**：
  ① **"没反应"要先问"主线程是不是被占着"**，而不是先怀疑事件绑定或状态同步 —— 后两者会留下日志，
     前者什么都不留（这正是它难认的原因）。**常驻一个长任务看门狗**，把"卡了多久、卡在哪一段"
     变成一行日志，比下一次再猜一轮便宜得多。
  ② **诊断本身也会变成热点**：`follow()` 那一格里的几何读只为日志服务，而日志大多被节流掉 ——
     凡是"为了记一笔"去读几何的地方，先问它会不会被记下来（同 #44 的家族）。
  ③ **别用"往全局 console 打补丁"去断言客户端日志**：扩展宿主的 `console` 与裸 node 未必是同一个
     对象，抓不到（本仓白掉过一次，见 `chat-client.test.ts` 里的说明）。要么走客户端自己的通道
     （`clientLog` / 纯函数判据），要么只断言行为。
  ④ **合成的量不出来的就别硬说**：这一轮的探针（`#mdsliceprobe`）按"整批一次 vs 分帧"对照，
     但合成条目比真机便宜两个数量级（20ms vs 50s），于是它只能证明"批次不再落在单任务里"，
     不能证明真机修好 —— 结论写在 §5.46 与验收 211 里，别让探针的数字冒充真机结论。

## 54. 把"一次请求的结果"当成终身真相 —— 会变的候选被冻结在第一次

- **日期**：2026-10-08（`CUSTOM-20261008-203`）
- **现象**：用户报「刚通过 Browse 选择的目录（并且发起了对话），但最近使用里没有这个记录」。
- **根因**：目录抽屉的候选（工作区文件夹 / **最近用过** / 默认）来自宿主的一次 `listDirectoryChoices`，
  而客户端把它存进 `choices` 后**再也不重新请求**（连 `reset()` 都不清）。那份列表是**会变的**（Browse
  选的目录、刚用过的目录都要等宿主把它们算进最近列表）⇒ 一份当天的快照用一整天，新目录永远不出现。
  **不是宿主没记**：真机日志里那次 `session/new` 的 `cwd` 就是 `d:\Git\zgithub\custom-marktext`（不是本工作区），
  也就是说宿主的"最近用过"里**有**它 —— 只有客户端这一侧还举着旧名单。
- **修法**：**每次打开抽屉都回头问一次**（stale-while-revalidate）：先用手上那份渲染（列表永远瞬间出来），
  回复到了再重渲染；`pending` 只表示"一条候选都没有"，不能每开一次都亮 Loading…。**同时限定只在
  "还没数据"与"打开时"问** —— 同一个 `refresh` 也被 boot 在切草稿/切会话时调用（那时抽屉是关的），
  不能每次都付一次宿主往返（回复里可能带一次 `session/list`）。
- **教训**：
  ① **缓存之前先问"它会不会变、变了谁知道"**：这类"服务端候选"（目录、会话列表、可选模型、命令表）
     的正确形态几乎都是"打开时回问一次 + 先渲染手上的"，而不是"取一次用到底"。
  ② **别把"我没重新问"读成"对方没有"**：症状是"最近使用里没有这个记录"，听起来像宿主没记，
     而真相是客户端在举旧名单 —— **先去日志里核对那一侧的实际数据**（`session/new` 的 `cwd` 就是铁证），
     再决定改哪边（同 #30 的家族：把"我手里没有这个信息"读成"这个东西不存在"）。
  ③ 缓存的**失效点**要跟着"用户的动作"走：这里的动作是"又用了一个新目录"，而它发生在抽屉**关着**的时候，
     所以唯一可靠的触发点是"下一次打开"。

## 55. 「偏好回话」被当成「命令」—— 每次广播都把一次状态迁移重放一遍

- **日期**：2026-10-08（`CUSTOM-20261008-204`）
- **现象**：用户报两条 —— ①「点一下地址栏的 Times，右侧大纲栏自己打开了（点之前是关着的）」；
  ②「关掉右侧栏、重启编辑器再打开面板，它又开着（预期是按会话保存开关状态）」。
- **根因**：一句话 —— **偏好里混了"此刻是否可见"**。`applyPrefs` 里写着 `isOpen = (mode === 'sidebar')`：
  于是"宿主的偏好回话"每次都等价于"把侧栏重新打开"。而那条回话是**广播**的（宿主在**任何**
  `setUiPref` 之后都回一次，给另一个面同步用）⇒ **任何**触发一次偏好写的动作（点 Times（200 起它会
  写）、拖 tab（198）、拖大纲栏宽度）都会把刚关掉的侧栏弹回来。而"关"本身只改了瞬态 `isOpen`、没落盘，
  所以重启后又按 `mode` 重算成"开着"。
- **修法**：把"开/关"变成**按会话持久的状态**（`outlineOpenBySession` + `outlineOpenDefault`，同 Times 那套），
  `isOpen` 一律从它推出来；关闭（☰ / Escape / ✕）都落盘；`applyPrefs` 只让两端**收敛**，不再拿它当命令。
  旧记录按老行为迁移一次，避免升级后侧栏无声消失。
- **教训**：
  ① **"偏好"与"此刻的界面状态"是两种东西**，别塞进一个字段：前者是"用户希望怎样"（会回话、会跨窗口），
     后者是"现在长什么样"（瞬态）。把后者从前者的**回话**里派生出来，就等于让每次同步变成一次用户动作。
  ② **凡是"回话即生效"的消息，先问它会不会被**广播**、以及接收方会不会把"收到"误读成"用户刚做的"**
     （#29 的兄弟：那条讲"没变化就不回话"会让客户端永远不一致，这条讲"每次都回话 = 每次都重放"）。
  ③ **状态按什么维度记，要跟用户的心智一致**：侧栏里是**这个会话**的大纲，A 开着不代表 B 要开着 ——
     用户直接把这条期望说出来了（"预期是按会话保存"）。凡是"属于某个东西"的状态，先问它属于谁（#38）。

## 56. 「同一条通道」不等于「同一个来源」—— 新的一类注入块永远在那儿等着

- **日期**：2026-10-08（`CUSTOM-20261008-205`）
- **现象**：用户报「用户对话里附加的文件没有合并到一个对话里（预期是跟图片附件一样显示），现在是分成了
  两条对话」—— 同一条消息渲染成**两个**蓝色气泡：一个只有 `<ide_opened_file>The user opened the file
  …</ide_opened_file>` 的原文，一个才是正文。
- **根因**：`<ide_opened_file>` 是 IDE（官方 Claude Code 扩展）注入的"当前打开的文件"**上下文**，
  它跟 109 处理过的那批（`<task-notification>` / `<system-reminder>`）一样走 `user_message_chunk`
  通道 ⇒ 被无条件当成"用户说过的话"。**109 当年只列了当时见过的五个前缀**，新的一类注入块出现时，
  没有任何东西会提醒你它存在 —— 症状是"多出一个气泡"，不是报错。
- **修法**：认形状前移 —— `<ide_opened_file>` 抠出路径，作为**文件 chip 挂到同一条消息的用户气泡**上
  （官方插件就是这么画的），块本身不建记录；其它 `<ide_*>` 块归 109 那条路（进前缀表，变成 meta 提示条）。
- **教训**：
  ① **通道相同 ≠ 来源相同**：`user_message_chunk` 这类"用户消息通道"里混着 IDE 注入、系统提醒、
     后台任务回报。**看到一个不认识的 `<xxx>` 前缀，第一反应该是"它是不是又一类注入"**，而不是
     "用户怎么会发这个"。
  ② **不同的注入块该有不同的形状**：任务回报是"提示条"（109），而"当前打开的文件"应该变成
     **消息上的 chip**（它确实是这条消息的上下文）—— 一律降级成提示条也不对，形状要跟着语义选。
  ③ **配对要靠数据里的键，不要赌到达顺序**：同一条消息的两条 chunk 在回放里带同一个 `messageId`，
     用「会话::messageId」暂存/取走（取过即删）比"上一个 chunk 是注入块"稳得多 —— 后者在顺序反过来
     （正文先到）时会把 chip 挂到别的消息上。

## 57. 用「结构」当布局判据 —— 新加一种同类成员就漏一处

- **日期**：2026-10-08（`CUSTOM-20261008-206`）
- **现象**：用户报「引用的文件 Tag 应该放在折叠按钮同栏（与引用图片一致）」—— 图片 chip 一直在
  caret 那一行，而**文件** chip 掉到了第二行。
- **根因**：112 给"图标/caret/chip 同在第一行"打的那条 CSS 判据是
  `summary:has(.content-image-chip)` —— 它按**具体的成员类名**（图片 chip）来认"这个气泡有 chip"，
  而不是按"有附件"这件事。文件 chip 走的是 `resource_link` 分支，外面多套一层 `.chip-row`
  （块级 div）⇒ 判据不成立、那一层还自己占一行。**同一件事（气泡里有 chip）在两处用了两种结构**，
  于是布局只对了其中一种。
- **修法**：判据补上文件 chip 那种结构（`:has(.chip-row)`）并让包装层 `display: contents`
  （它只是个 div 壳，不该占盒）；顺带把 tag 加高、加 `</>` 图标。
- **教训**：
  ① **布局判据要认"这件事"，别认"当前这一种东西"**。`has(.content-image-chip)` 写起来最省事，
  但它把"有附件"这个语义绑死在图片那一个类名上 —— 加一种新附件（文件 chip、以后还有引用/链接）
  就静默漏一处。**要么给容器一个显式的类**（如 `has-attachments`，由构造方写），要么把**所有**
  同类成员一起列进判据并写清"加成员时必须同步这里"。
  ② **同一个渲染函数服务于多处时，看它返回的壳**：`renderContentItem` 对图片返回 chip 本身、
  对 `resource_link` 返回 `div.chip-row` —— 消费方（用户气泡、工具卡）拿到的东西形状不同，
  而"形状不同"正是这类布局 bug 的来源。改一处渲染前先问"还有谁吃这个返回值"。
  ③ 有一半的"顺带"其实是用户明确提的：这一轮的三条里，加高 tag 与加图标都是用户点名的观感问题，
  别只修那条报出来的（"同栏"），另外两条一起做掉。

## 58. 「同一条」的判据窄了 ⇒ 用户的第二次动作被静默吃掉

- **日期**：2026-10-08（`CUSTOM-20261008-207`）
- **现象**：用户要求"同一个文件能引用**多段**"（框选 12-40 引用一次，再框选 5-9 还能再引用一条）。
  实现时才发现：**两处按"路径"做的同一性判断**会把第二段静默吃掉 ——
  ① 宿主 `addAttachments` 的去重是 `list.some(existing => existing.path === attachment.path)`
  ⇒ 同一个文件的第二段**直接不入列**；② `detachFile` 是 `filter(a => a.path !== path)`
  ⇒ 点掉一段会把同一个文件的**所有**段一起删掉。两处都不会报错：界面上只是"点了 `+` 没反应"、
  "删了一个少了两"。
- **根因**：同一性（"这两条是不是同一条"）的定义**比用户的语义窄**。用户语义是"文件 + 行区间"，
  代码里写的是"文件"。在只有一个维度的时候两者恰好等价（拖拽进来的文件没有区间），所以看不出问题；
  一旦多出第二个维度（区间），窄的那个判据就把不同的东西当成同一个。
- **修法**：同一性收敛到**一个函数** `sameReference(a, b)`（宿主的去重与客户端"加过没有"共用同一套
  判据），`detachFile` 带上可选的区间（带 = 只摘那一段，不带 = 整条路径全摘，拖拽/粘贴的旧行为不变）。
- **同一轮踩的第二个坑（同一族）**：草稿页把附件投影给 `state.attachments` 的那个小函数
  (`draftFilesOf`) **只手抄了 `{id,kind,name,path}`** ⇒ 区间在投影时掉了，"这一段加过没有"永远答"没有"，
  同一段能被攒下两次。**投影函数（挑几个字段拼个新对象）是漏字段的天然温床**：改数据结构时，
  要么直接传引用，要么在投影里一次写全并留一行"加字段要同步这里"。
- **教训**：① **先问"用户的'同一条'是几个维度的"**：路径、路径+区间、路径+时间戳…判据窄一格就是静默
  丢数据。② **同一性只能有一份**：宿主去重与客户端判断各写一遍，改一处忘另一处就变成"能加不能删"。③ 凡是
  `filter/some` 里出现 `===` 比较对象身份的地方，都值得回头看一眼"这个身份够不够"。

## 59. 两态"看得出来不同"要用**量**来定，不能拿语义相近的 token 凑

- **日期**：2026-10-08（`CUSTOM-20261008-208`）
- **现象**：用户要求"加一些按钮背景色区分预选与已引用的文件"。第一版给预选态挑了
  `--vscode-badge-background`（语义上"像个徽标"，看着最像"强调"），而**已引用态**用的是
  `--vscode-textCodeBlock-background` —— 在预览的主题里这两个 token **恰好是同一个灰**
  （都是 `rgb(43,43,43)`）⇒ 两态一模一样，改了个寂寞。
- **根因**：把"我应该用哪个 token"当成了**语义选择**（强调/中性），但真正要保证的是**度量结果**
  （两态的实测底色不同）。不同主题把它们映射成同一个值的可能性是存在的，光看名字看不出来。
- **修法**：预选态的底色改成**从中性 chip 底色混入主题强调色**：
  `color-mix(in srgb, var(--vscode-focusBorder, var(--vscode-panel-border)) 30%, var(--vscode-textCodeBlock-background))`
  —— 两态的差值是**构造出来**的，不再依赖"两个 token 恰好不同"；再叠加虚线/实线，多一条通道。
- **怎么发现与怎么防**：`preview-records.mjs` 的 `#refchip` 档探针**把两态各读一遍**
  （读出当前态 → 用 setAttachments 翻一次 → 再读），一次就看见两个 rgb 完全相同。
  **凡是"两态要用视觉区分"的改动，探针就该把两态的 `getComputedStyle` 各读一次并当场对比** ——
  截图只有一张、肉眼也容易忽略"只是差一点点"，而两个 rgb 摆在一起是骗不了人的。
- **附带的教训**：探针自己翻转状态时必须**满足业务同一性**（这里是 207 的"路径 + 区间"）——
  第一次翻转只给了路径，探针读到的是"翻不过去"的旧态，差点被读成"样式没生效"。

## 60. 客户端模块之间的接线错误，在桩 DOM 里是**静默**的 —— 只有真接线才验得出

- **日期**：2026-10-09（`CUSTOM-20261009-209`）
- **现象**：会话恢复做完了，桩测试全绿（卡片画得对、按钮文案对、tab 也对），可真机预览里点【Restore】
  **什么都没发生** —— 不报错、不发消息、卡片也不变。
- **根因**：`restoreChoice` 本该挂在 **`NS.boot`** 上（卡片调 `NS.boot.restoreChoice(...)`），而我把它
  写进了 **`NS.draft`** —— 因为当时的锚点是 `drop: dropDraft,`（那是 `NS.draft` 那节里的行）。
  而卡片的调用点写着 `if (NS.boot && NS.boot.restoreChoice) { ... }`（防御式判空 ⇒ 找不到就静默跳过）。
  **两边各自都"对"**：桩测试里 `NS.boot` 是个随意铺的替身，写什么进去都收，于是判空永远为真、永不算错。
- **怎么发现的**：真 Chromium 的 `#restorecardprobe` 档把"点一下之后客户端发出去的是什么"读出来
  （`posted: [...]`），一眼看见只有 `ready` 而没有 `startRestore`；再把 `!!(NS.boot && NS.boot.restoreChoice)`
  也读出来，才是 `false` —— **两个读数一起**把"没接上"与"没触发"分开了。
- **教训**：
  ① **判空的调用点 + 写错的对象 = 最安静的一类接线错误**。跨模块调用要么让缺失**出声**
     （缺了就打一行 `console.warn`），要么在真环境里有一条读数证明它接上了 —— 本仓的日志桥就是干这个的。
  ② **桩 DOM 测不出"接线"**：它测的是"逻辑正确时行为正确"，而接线错的是"逻辑根本没被调到"。
     凡是**新加一条跨模块调用**，就要有一条**真环境**的读数（预览档读"发出去的消息类型"最省事）。
  ③ 锚点选错位置会静默地写进**同形但不同**的对象（`NS.boot` / `NS.draft` 都是 `{...}` 字面量）：
     往字面量里插字段时，**先看清这个字面量属于谁**（本文件里 `drop: dropDraft` 是 `NS.draft` 的成员，
     而 `requestMarkdown` 才是 `NS.boot` 的）。
